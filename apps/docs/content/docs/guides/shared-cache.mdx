---
title: Shared cache
description: Share one better-supabase cache entry between callers who hold the same grants, and skip the live version read for writes that Postgres checks again.
---

`authorizationHooks` sets `shareKey`, the hook better-supabase calls to key a `share: "tenant"` cache entry. Callers in one tenant whose grants for the entry's permissions are equal get the same key and read one entry. The entry is still filled through the caller's own client under RLS.

## Grant fingerprint

`grantFingerprint(permdock, permissions)` from `permdock/better-supabase` returns `gf1:` and a SHA-256 digest of what the instance grants for `permissions` in its tenant. It leaves out the user id and the names of the roles, so an editor and an admin that grant `quote.read` under the same terms get the same digest.

It returns `null`, and the entry stays per user, for:

- a permission the policy does not declare, or an empty list;
- an instance without a principal or a tenant, or a delegated or simulated one;
- a grant whose condition is `opaque`, a `sqlFunction`, a `liveSession` check or not portable;
- an instance that grants none of the permissions.

The hook adds three cases: a token marked truncated in `team_ids_truncated` or `permissions_truncated`, a token whose `authz_ver` is behind the version in `runtime.versions`, and a subject that is not a user. A token with `memberships_truncated` answers only in the case described under [truncated tokens](#truncated-tokens).

## Truncated tokens

When the size budget cuts a user's memberships, the token carries `memberships_truncated: true`. `shareKey` still answers for the active tenant when the token holds at least one entry outside that tenant. The hook ranks the active tenant's entries first and keeps a prefix of that order, so a kept entry of another tenant means the prefix passed every entry of the active tenant. The digest then covers exactly the entries the database holds for the tenant. With only active-tenant entries, or none, the cut may have fallen inside them, and `shareKey` returns `null`. A cut that dropped `attrs` does not change the grants, so it does not block a key. `tests/better-supabase/share-key.test.ts` covers the three cases and `tests/integration/src/hook-token-shape.test.ts` the ranking.

Doctor [PD138](/docs/cli/doctor#pd138-users-the-budget-truncates) counts the users the budget truncates, so you can see how many requests skip the key.

## Provider tables

`authorizationProvider({ manifest, catalog, tables: true })` fills better-supabase's `tables`. For each resource the manifest maps to a table it lists the keys of the `read`, `list` and `get` permissions and marks the table `tenant` only when every one of them is held at the tenant scope alone, carries no row condition and has a grant. A resource with a restriction, a field mask or a grant at another scope is `row`. Without `tables: true` the provider sets none, and every entry stays per user. Doctor BS428 checks each entry against the generated select policies.

When `permdock.manifest.json` has `rls.tableReads`, the provider answers from it instead, keyed by the qualified table (`public.orders`). `permdock supabase inspect` writes `rls.tableReads` from the select policies the schema files, migrations and `rls.out` leave defined, so hand-written policies count too. A table is `tenant` only when:

- row level security is on and the table has no field view;
- every permissive select policy for `authenticated` is `<column> in (select <schema>.permitted_<root>_ids_by_permission('<key>'))` on one column, written by hand or rendered from an `@bsb access` tag;
- every restrictive select policy reads no column of the row, such as one that checks the session.

Every other table is `row`, with the rules it breaks:

| Rule                     | The table has                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------- |
| `form`                   | a policy on the plain `permitted_<root>_ids(key)`; `permdock codemod bsb-access-tags` moves it to a tag |
| `follows`, `via`, `walk` | a policy that calls a `follows`, `via` or walk helper                                                   |
| `owner`                  | a policy that compares a column with `auth.uid()` or `permdock_user_id()`                               |
| `condition`              | another select expression, or tenant policies on two columns                                            |
| `restrictive`            | a restrictive select policy that reads a column                                                         |
| `fields`                 | a field view                                                                                            |
| `unknown`                | row level security off, or no permissive select policy                                                  |

Tables in the helpers' schema, `better_supabase` and the platform schemas are left out. The manifest is read from the files on disk, so run `permdock supabase inspect --out` after `permdock generate` changes a select policy. [Doctor PD128](/docs/cli/doctor#pd128-a-tenant-table-that-reads-by-row) fails when the committed manifest marks a table `tenant` that the files now make `row`.

## Make a `form` table tenant

A `form` table has a select policy on `permitted_<root>_ids('<key>')`. `permdock codemod bsb-access-tags` moves it to a tag, and the table becomes `tenant`, when every grant of the key is an allow of that key with no condition and no deny. When it leaves the policy, `permdock codemod bsb-access-tags --check`, `permdock rls report` and `permdock rls explain` name the first grant that decides it, and `rls.tableReads[].reason` in the manifest holds the same sentence.

| Reason                                                      | What the app changes to make the table `tenant`                                                                                                                                       | When it must not                                                                                                  |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `role R on S denies it`                                     | Remove the deny and leave the permission out of the role that should not read; or give the deny's roles a permission of their own and check that in the policy.                       | The deny hides rows from some holders only. Another holder's cached rows would reach them.                        |
| `grants it under a condition (grant key k#n)`               | Drop the condition when it restates the tenant scope. Otherwise split the permission: `k` unconditional for the tenant list, `k.own` with the condition for rows.                     | The condition reads the row or the caller (`ownerId`, a level such as `k@own`, a status). Rows differ per holder. |
| `grants it through another key (grant key g)`               | Check the key the role holds in the policy, `g`, or grant `k` itself.                                                                                                                 | Two roles hold different keys that the policy treats as one. The policy answers per role.                         |
| `under a row condition or a validity window`                | Remove the window or the `requires`; a window changes the answer with the clock, so keep it off a shared table.                                                                       | The grant expires per member.                                                                                     |
| `every grant of it is unconditional` and still kept         | Read the codemod's `kept` line: another policy for the command, a tenant column that differs from the table's other policies, or a role other than `authenticated`.                   | The second policy filters by row.                                                                                 |
| `policy P is still defined in F next to an @bsb access tag` | Write the migration that drops `P` (`supabase db diff`). The tag renders the replacement policy; until a migration drops `P`, the database holds both, and the table reads as `form`. | Never: the table is already `tenant` in the schema files.                                                         |

After the change run `permdock generate`, `permdock codemod bsb-access-tags`, `permdock supabase inspect --out` and both doctors. Doctor BS428 then checks that the tag and the policy agree. A table that reads one row per member (`owner`) or per condition stays `row`, however many members hold the key: sharing it would serve one member's rows to another.

A table shares per tenant only when its select policy filters by permission and not by row. Prove it per entry with `expectTenantShare` from `better-supabase/testing`: two callers with the same grant get the same key and read the same rows, and a member without the grant gets no key.

## Shared functions

`authorizationProvider({ manifest, catalog, tables: true, sharedFunctions: true })` fills better-supabase's `sharedFunctions`: the functions a `share: "tenant"` fill may call. `permdock supabase inspect` writes `rls.sharedFunctions` into the manifest, one entry `{ function, tables, permissions }` for each function the schema files, migrations and `rls.out` define that passes better-supabase's BS430:

- `language sql`, `security invoker`, `stable` or `immutable` (a function that states no volatility is `volatile` and is left out);
- no `auth.*`, `current_user`, `session_user`, `current_setting` or helper of the helpers' schema;
- every function it calls is itself listed, or a built-in;
- every relation it reads is a `tenant` table in `rls.tableReads`, resolved through `[<function schema>, public]` like better-supabase does.

`permissions` is the union of the keys those tables check. A function that reads one `row` table is not listed. An overloaded name is listed when every overload qualifies. `sharedFunctions: true` needs `tables: true` and a manifest from `inspect` 0.31 or later; the provider names either gap in `problems`.

[Doctor PD137](/docs/cli/doctor#pd137-a-shared-function-that-reads-a-row-table) fails when the committed manifest lists a function that the files now make read a `row` table or the caller. better-supabase's BS430 checks the same properties on the database.

## Helpers that answer the same for equal grants

Two callers with an equal `grantFingerprint` for a key hold the same grants of that key in the tenant. A helper gives them the same answer only when its result depends on nothing else. `permdock supabase inspect` writes the helpers that do into `rls.tenantPureHelpers`, with the argument that holds the key and the argument that holds the tenant:

| Helper                                                               | Key argument | Tenant argument | Why it is the same for equal grants                        |
| -------------------------------------------------------------------- | ------------ | --------------- | ---------------------------------------------------------- |
| `permdock_<root>_has(p_grant, p_tenant)`                             | `p_grant`    | `p_tenant`      | It tests one grant key in one tenant.                      |
| `permitted_<root>_permission_keys(p_id, p_keys)` (`p_keys` overload) | `p_keys`     | `p_id`          | It lists which of `p_keys` the caller holds on one tenant. |

The answer is the same only when the tenant argument is the entry's tenant and the key argument is one of the entry's `permissions`. A call with another tenant reads grants the fingerprint does not cover.

These helpers are left out, and the guide says why:

| Helper                                                                                    | Why callers with an equal fingerprint differ                                                                            |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `permitted_<root>_ids_by_permission`, `permitted_<root>_ids`, `permitted_<root>_id_array` | They list every tenant the caller holds the key in. A caller who is also a member of another tenant gets a longer list. |
| `permdock_has`, `permdock_has_permission`                                                 | They answer for the global scope, not for the tenant.                                                                   |
| `permitted_<resource>_rows`, `permitted_<resource>_ids`                                   | They decide per row, through restrictions, instance grants and row conditions the fingerprint does not cover.           |
| `permdock_subject`, `permdock_bootstrap_permissions`, `permdock_user_id`                  | They read the caller.                                                                                                   |

`tests/integration/src/tenant-pure-helpers.test.ts` checks both lists on PGlite: callers with an equal fingerprint get one answer from each listed helper, and `permitted_<root>_ids_by_permission` returns `acme` for one and `acme, beta, delta` for another. `permdock_<root>_has` takes the grant key, which equals the permission key for an unconditional allow.

A function can call a listed helper only if better-supabase's BS430 accepts the call and adds the key to the share key. It does not today: BS430 refuses every call into the helpers' schema. The request is in [better-supabase requests](https://github.com/ScaleDockHQ/permdock/blob/main/docs/agents/better-supabase-requests.md).

`node scripts/centrakit-dry-run.ts --stack` copies CentraKit, runs the 0.31 codemods and `generate`, sets `tables: true` and `sharedFunctions: true`, starts the copy's local Supabase stack, loads its schema files with `supabase db schema declarative sync` and runs `permdock rls verify --shadow` and better-supabase's doctor against it. The report is `scripts/centrakit-dry-run.json`. It ran on 24 November 2026 with better-supabase 0.85.0 and Supabase CLI 3.3.0.

| Check                                                            | Result                                                                                             |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Tables in `rls.tableReads`                                       | 256: 28 `tenant`, 228 `row` (65 `form`, 54 `owner`, 90 `condition`, 6 `restrictive`, 16 `unknown`) |
| `rls verify --shadow`                                            | no findings: the schema files and the database agree on policies, functions and grants             |
| BS430 on the 4 functions of `rls.sharedFunctions`                | 0 findings                                                                                         |
| BS429                                                            | 0 findings                                                                                         |
| BS409                                                            | 3 warnings about `blocks.permissions.activeTenant` and `disabled`, which are CentraKit config      |
| BS428 on the 28 `tenant` tables                                  | 28 findings, `its select policies check []`                                                        |
| The same 28 tables with `::text` removed from `pg_policies.qual` | 28 of 28 check exactly their `permissions`                                                         |

The 28 findings are not a table fault. better-supabase 0.85.0 matches the provider's `permitted_{scope}_ids_by_permission({permission})` template against `pg_policies.qual`, which Postgres stores as `permitted_organization_ids_by_permission('asset.read'::text)`; the pattern expects `)` after the literal and finds `::text`. The release therefore does not state that the 28 tables pass BS428: they pass once better-supabase reads the cast ([request](https://github.com/ScaleDockHQ/permdock/blob/main/docs/agents/better-supabase-requests.md)). The dry run found two PermDock faults and fixed them: `rls.tableReads` kept a table a later migration drops or renames (27 stale entries, which BS428 reported as `the database has no such table`), and `permdock rls verify --shadow` looked for `supabase/schemas` in the package directory, so it found no file in a monorepo whose `supabase/` sits at the root.

## Writes that RLS checks again

better-supabase sets `context.enforcement` to `rls` on a write that Postgres checks on current data. `authorizer` maps such a write to the `database-write` intent: `claimsFirst` takes the authorization version from the shared cache, as for a read. A role change inside the cache window can therefore let PermDock admit a write that RLS then refuses, and it cannot admit a write RLS would also accept on stale data. A write with `enforcement: "definer"`, or without it, reads the version live.

```ts
authorizer({ policy, memberships, versions });
```

## Version store

`memoryVersionCache({ shared })` takes a `VersionStore` with better-supabase's shape: `get(id)` answers `{ version, at }`, `set(id, version, at)` writes the time of the database read, and `delete(id)` forgets. `maxStaleMs` counts from `at` on every instance, so a store that never expires cannot keep a version past it. A stored entry dated in the future counts as read now, and one older than `maxStaleMs` is a miss.

| Store                                         | Use it when                                                                                         |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `runtimeCacheVersionStore(getCache())`        | The app runs on Vercel; entries expire after 60 s.                                                  |
| `postgresCacheVersionStore(pool, "schema.t")` | The app has no runtime cache; the table is `(user_id text primary key, version bigint, at bigint)`. |

`testVersionStore` from `permdock/testing` checks a store against that shape.

## Warm the first request

`authorizationHooks(...).warm()`, `authorizer(...).warm()` and `warm(policy)` from `permdock/next` build one anonymous instance and run one `can`. They never reject: a failure answers `{ ok: false, ms }`. Call one in `instrumentation.ts` after the policy import, so the first request does not pay for the instance.

```ts title="instrumentation.ts"
export async function register() {
  const { warm } = await import("permdock/next");
  const { policy } = await import("./src/policy");
  await warm(policy);
}
```

`node scripts/authz-latency.ts` measures these against the local Supabase stack of `apps/examples/next-better-supabase` and writes `scripts/authz-latency.json`. The cold instance is above the 3 ms threshold of a compiled policy index: on the fixture's 273 keys and 1,790 grants, `definePolicy` takes 14.9 ms, the first `getPermDock` 1.0 ms and the first `can` 1.4 ms. Importing the policy in `register()` moves `definePolicy` out of the first request, which then pays 2.4 ms.

At 17.30 ms the fixture is over the 3 ms at which a compiled `policy-index` kind would ship, and the example, at 6.44 ms, is too. PermDock 0.31 does not ship it: the profile puts most of `definePolicy` in the SHA-256 digest of the canonical policy string, and a check of the grant count and key order cannot tell a stale digest from a current one. Import the policy in `register()` instead.

`grantFingerprint` made no source call on a built instance, and the hook read no membership. Without a version cache, `permdockFor` read `version` once per hook call; with `versions: memoryVersionCache()` it read it once in 10,201 calls.

Variant B stores `permdock_token_current()` once per transaction and cuts the helpers' mean by 4.5% (0.403 to 0.385 ms) and 3.3% (0.430 to 0.416 ms), under the fifth a variant needs to ship, so the generated helpers stay as they are. Buffers are shared hits per statement.

The Server Action asks `database-write` for its update instead of `write`: RLS checks the row again on current data, so the cached version cannot grant the row change itself, and a role change shows within the 5 second window for reads and at once for a write that RLS does not check again (`definer` or no enforcement stays `write`).

The two members share a `bsb.kept` entry only through the key. The fingerprint covers grants, not the tenant id: admins of two organisations get the same string, so a key for tenant data adds the tenant.

The 8 keys and 6 roles of the fixture are CentraKit's target model, not its 0.28 policy; the policy module's 35.73 ms is the `zod` import plus `definePolicy`. `warm()` moves `getPermDock` and the first `can` out of the first request and costs the same 1.24 ms at boot.
