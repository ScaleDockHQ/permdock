`permdock/better-supabase` connects PermDock to [better-supabase](https://bettersupabase.com/docs/extending/authorization-providers). better-supabase verifies tokens, builds sessions and owns the data layer; PermDock owns roles, permissions, the claim contract and the one token hook. better-supabase never imports PermDock: it reads a versioned `AuthorizationProvider` object from its config, and this entry builds that object and the other values its slots take from the files PermDock already generates.

The entry needs `better-supabase` 0.29 or later as a peer (`>=0.29.0`). The range has no upper bound: CI tests 0.29.0 on every pull request, and a daily job tests the newest release.

Everything on the [Supabase page](/docs/adapters/supabase) still applies: the hook, the helpers and the claims are the same with or without better-supabase.

## Why

- better-supabase has slots, not a PermDock mode. Its config takes an `authorization` provider, a bucket or topic takes an `access` policy, and its API key block takes a claim and a verifier. Each slot is a neutral, versioned contract (`apiVersion: 1`), so PermDock fills it the way `permdock/better-auth` fills Better Auth's role source, and any other authorization package could fill it too.
- The provider is data built from the manifest. `permdock supabase inspect --out` already writes `permdock.manifest.json` with the helper schema, the scopes, the membership tables and the hook's claims. `authorizationProvider` maps that file to the contract, so better-supabase's SQL and doctor follow the helpers `permdock rls generate` wrote without reading a PermDock file themselves.
- `permdock/supabase` stays plain Supabase. It names no better-supabase identifier, and an app on `@supabase/supabase-js` or `@supabase/server` alone never loads this entry.

## API

```ts
import {
  authorizationProvider,
  authorizer,
  bucketPolicy,
  topicPolicy,
  apiKeyVerifier,
  apiKeyClaimOptions,
  subjectFromBetterSupabase,
  subjectFromShareLink,
  toolPolicy,
  credentialGuard,
  hookCan,
  handlerCan,
  supportPolicy,
  subscriberPolicy,
  principalSource,
  principalFromMemberships,
  accessReviewApplier,
  authorizationHooks,
  roleOrderFromCatalog,
} from "permdock/better-supabase";
```

- `authorizationProvider({ manifest, catalog?, scope?, approver?, approvers?, activeTenant?, rowHelpers? })` returns better-supabase's `AuthorizationProvider` (`apiVersion: 1`, `name: "PermDock"`). `manifest` is `permdock.manifest.json`, parsed or as JSON text; `catalog` is `permissions.catalog.json`. Without a catalog the provider lists no permissions, so better-supabase refuses every key a bucket, topic or module checks, and `problems` asks for it. `scope` names the tenant scope and defaults to the manifest's one root scope.
- Its `functions` call `permitted_<scope>_ids_by_permission`, `member_<scope>_ids`, `permdock_has_permission` and their `_for` forms in `rls.schema`. These take a permission key and subtract the instances a deny of it reaches, so a permission split into `#n` grant keys still matches. `permissionsFor` calls `permitted_<scope>_permission_keys_for`, so better-supabase's `member_permissions` lists a member's keys; like the other `_for` templates it is set only when the manifest lists the helper, which `rls.mode: 'database'` writes.
- `canAssign` and `canAssignFor` call `permdock_can_assign` and `permdock_can_assign_for`. When the manifest's `rls.customRoles` is set and the tenant scope is a root scope, they call `permdock_can_assign_any` and `permdock_can_assign_any_for` at the tenant scope instead, so better-supabase's `can_assign` and `can_assign_as` also answer for a custom role.
- `holdersOf` is `permitted_<scope>_users(permission, tenant)`, the user ids holding a permission in a tenant, for a notification's audience. `actorMayWrite` is `permdock_actor_may_write()`, which the inbox and workflow modules call before a write. Each is set when the manifest lists its helper, with the role that runs it in `requires`.
- `teamIdsOf` is `member_<scope>_ids_of(user)` for a scope named `team` or `teams`. With `blocks.permissions.model: 'provider'`, better-supabase's `team_ids_of()` and the team-sharing policies of `saved-views` and `collections` call it instead of reading the teams block. The helper answers only for the caller and returns no rows for another user's id. `team_ids_of()` itself refuses a signed-in caller who names another user with `TEAM_FORBIDDEN`; the service role and direct database sessions still pass through. It is set when the manifest lists the helper. `permdock rls generate` writes it for a team scope with membership sources; without one, `permdock supabase hook generate` writes `member_team_ids_of` from `supabase.hook.teams` ([teams](/docs/adapters/supabase-hook#teams)). With neither, `team_ids_of()` reads the teams block, and doctor reports `BS417`.
- `permitted` answers better-supabase's `permitted(resource, id, permission)`: for a resource that names a scope, whether `id` is among `permitted_<scope>_ids_by_permission(permission)`; for any other resource, whether the key is granted in the tenant. That second branch only holds for a key the catalog marks `rowConditions: false`; a key with row conditions is `false` there, so its table policies decide.
- `operations` lists each catalog [operation](/docs/concepts/operations) as better-supabase tools: a name without a dot becomes `ai.tool.<name>` and `mcp.tool.<name>`, and a dotted name is used as written. `risk: 'critical'` maps to `high`, and the effects `send` and `spend` to `external`.
- `delegation.scopes` maps each catalog permission's `.scope` to its key, so an OAuth client or agent token granted `invoice:read` gets `invoice.read`. Each coarse scope in the catalog's `oauthScopes` maps to the keys it covers ([OAuth scopes](#oauth-scopes)). Keys are sorted by code point. A scope the catalog does not list grants nothing.
- `approver` is a permission. It becomes the `'ai-tool'` entry of `approvers` unless `approvers` names one. A key the catalog lacks is a problem.
- In a project with a readable `better-supabase.config.*` object export, the CLI defaults the hook's active source to `app_metadata.<rls.tenantClaim ?? tenant_id>`. An explicit `supabase.hook.activeFrom` or `--active-from` wins. Plain Supabase keeps `app_metadata.active_<first scope>`. This makes generation, inspection and PD078 agree without changing plain Supabase projects.
- `activeTenant` is better-supabase's `blocks.permissions.activeTenant`. When the token hook reads the active tenant from another place than better-supabase writes it, `problems` names the `supabase.hook.activeFrom` to set: `app_metadata.<tenant claim>` for `"claim"`, or the profile column for `{ profileColumn }`. Doctor reports the same as PD078.
- `rowHelpers: true` fills better-supabase's `rowsWith` and `rowsWithFor` from the `permitted_<resource>_rows` helpers that `rls.rowHelpers` writes and the manifest names. A better-supabase subject type whose action in `subjects.<type>.permissions` names `rows: "<resource SQL name>"` with a `key` then checks the rows the caller holds that key on, through the candidate form `permitted_<resource>_rows(permission, ids)`, and for another user through `permitted_<resource>_rows_for`. Without row helpers in the manifest, `problems` names the step to run.
- `tokenHook.activeOrganizationFrom` names where the token hook reads the active tenant, from the manifest's `hook.activeFrom`: `"claim"` for `app_metadata.<tenant claim>`, or `{ profileColumn, key? }` for a profile column. better-supabase's doctor BS409 warns when it differs from `blocks.permissions.activeTenant`. It stays unset for an `app_metadata` key other than the tenant claim, which better-supabase has no name for, and when `activeTenant` is `"resolver"`, where the tenant comes from the request.
- `approvers` maps each better-supabase request kind to `user()`, `holder()` or `anyOf()` approvers and fills `isApprover`, which better-supabase asks for every request that waits on an approval ([Approvers](#approvers)). It needs `permdock_is_approver`, which `rls.approvals` writes; without it `isApprover` is unset and `problems` names the helper. The provider never sets `canApprove`.
- The provider leaves `portalSubjects` and `portalParties` unset: PermDock has no guest grants, so better-supabase's `guests` block decides which records and parties a guest reaches.
- `scopes` carry each scope's `idType`: `uuid`, `text`, `bigint` or `integer`, with `int8`, `int` and `int4` normalised. Any other id type is a problem.
- `requires` lists each helper with the role that must execute it; `memberships`, `suspension` and `roleSources` come from `rls`; `tokenHook` names the hook function, the claims it owns and the `grantsCommand` that restores the hook's grants for the manifest's `hook.schemas`: `permdock supabase hook generate && supabase db schema declarative sync -f permdock_hook` under pg-delta, the `--grants-out` command under migra. A manifest written without `supabase.hook` (`rls.authorize: 'database'`) has no `hook` section, so `tokenHook` is absent. A manifest that cannot fill a field is recorded in `problems`, which better-supabase's doctor reports, and an invalid manifest throws a `TypeError`.
- `authorizer({ policy, subject?, operations?, memberships?, version?, versions?, intent?, onError?, options? })` returns better-supabase's `Authorizer` (`apiVersion: 1`, `name: "PermDock"`) for its `authorizer` server option. It decides every `permission` a resource, action, route guard or MCP tool declares ([Authorizer](#authorizer)).
- `bucketPolicy(access, options)` and `topicPolicy(access, options)` return the `access` policy for `defineBucket` and `defineTopic`. `access` maps the operations (`read`, `list`, `write`, `delete` for a bucket; `receive`, `send` for a topic) to permissions, and `options` is `{ manifest, catalog, scope, segment? }` or `{ policy, schema?, scope, segment? }`. With `policy`, the `definePolicy` result the app already imports, nothing is read at runtime: the scopes, the permissions with row conditions and the scopes each permission is granted at come from the definitions, and `schema` names the helper schema (`rls.schema`, default `permdock`). The checks below are the same either way. They call `permitted_<scope>_ids_by_permission` and `permdock_has_permission`, which check role and scope only and subtract denies, so a permission the catalog marks `rowConditions: true` (or a conditioned grant in `policy`), or does not grant at `scope`, throws. `scope: "platform"` checks a permission granted globally.
- `apiKeyVerifier({ keys, manifest?, serviceRoles?, allPermissions? })` is a `CredentialVerifier` over better-supabase's `createApiKeys()`, for [`subjectFromApiKey`](/docs/concepts/credentials#using-a-key). A personal key is a `user` credential acting as its user, a tenant key a `service` credential holding `serviceRoles` in its tenant, and the key's scopes are the credential's permissions. `serviceRoles` defaults to the manifest's `rls.apiKeys.serviceRoles`. A rotated key in its grace period verifies, and its credential's `expiresAt` is the end of the grace period when that comes before the key's own expiry. An invalid, revoked, expired or rate-limited key, and a failed lookup, verify to `null`.
- `apiKeyClaimOptions(manifest)` returns the `claim` and `tenantClaim` options of better-supabase's `apiKeyClaims()` and `apiKeyResolver()`, from the manifest's `rls.apiKeys`, so a key's token carries the scopes ceiling, tenant and roles the helpers read. It throws when the manifest has no `rls.apiKeys`.
- `subjectFromBetterSupabase(session, options?)` is `subjectFromSupabaseSession` with better-supabase's defaults: `memberships` for the memberships and the entitlements module's `features` claim for `principal.plans`. A `user` session maps through `subjectFromSupabase`. With `apiKeys: { permissions, manifest?, serviceRoles? }`, an `apiKey` session maps like `apiKeyVerifier`'s credential; without it, and for `anon`, `service` and `invalid` sessions, the subject is anonymous. `plans: { claim?, keys? }` decodes the short codes `entitlements.claim.keys` writes back to feature keys. Other options override the defaults.
- `subjectFromShareLink(token, { shareLinks, links, ttl?, linkPolicy?, onAuth? })` resolves a better-supabase share-link token into a link subject ([Share links](#share-links)).
- `toolPolicy({ permdock, data? })` returns the `authorize` and `visible` hooks of `createMcp` for tools whose `meta` is a permission ([MCP tools](#mcp-tools)).
- `credentialGuard(provider, { permdock, use, revoke? })` wraps a `CredentialProvider` so PermDock decides each token use ([Credentials](#credentials)).
- `hookCan(permdock)` and `handlerCan({ getPermDock })` return the `can` options of `authorizeHook` and `protectWebHandler` in `better-supabase/workflow-sdk` ([Workflows](#workflows)).
- `supportPolicy({ policy, subject?, options?, writable?, approval?, approved? })` returns the `authorize` option of `supportSessions` ([Support sessions](#support-sessions)).
- `subscriberPolicy({ policy, principals, events, row?, sender?, options? })` returns the per-subscriber check for an outbox, webhook or realtime fan-out ([Subscriber fan-out](#subscriber-fan-out)).
- `principalSource({ claims, identities?, subject? })` returns a `PrincipalSource` over the claims better-supabase mints ([Principals](#principals)).
- `principalFromMemberships(userId, rows, { scope?, tenant? })` builds a frozen `Principal` from rows of the `memberships` block's table (`BetterSupabaseMembershipRow`: `user_id`, `organization_id`, `role`, `disabled_at?`), for server code that reads the table instead of the token ([Server code](#server-code)).
- `accessReviewApplier({ client, reviews, policy, demoteTo?, email?, permdockFor?, schema?, scope?, now? })` applies the revoked items of an [access review](/docs/concepts/access-reviews) through the organizations and invitations blocks, then marks each one applied ([Access reviews](#access-reviews)).
- `authorizationHooks({ policy, claims, ... })` returns better-supabase's `AuthorizationHooks` for `createServer(betterSupabase, { authorization })` ([Authorization hooks](#authorization-hooks)).
- `roleOrderFromCatalog(catalog, { scope?, owner? })` returns the catalog's role keys highest first, for the SSO block's `roleOrder` ([SSO role order](#sso-role-order)).

## Setup

Generate the helpers, the hook and the manifest first, as on the [Supabase page](/docs/adapters/supabase):

```bash
SPLIT="--target sql --split helpers,seeds,indexes,policies,hook"
permdock rls generate $SPLIT --seeds-out -                    # the schema files under supabase/schemas
supabase db schema declarative sync --no-apply -f permdock    # their migration
permdock rls generate $SPLIT --seeds-out supabase/migrations/ # the role_permissions seeds, after it
permdock supabase inspect --out
permdock collect
```

That is Declarative Schemas 2.0, the default: `supabase/config.toml` needs `[experimental.pgdelta]` with `enabled = true`. A project on `supabase db diff` sets `supabase.schemas: 'migra'`, and one without declarative schemas sets `supabase.schemas: 'migrations'` ([schema workflow](/docs/cli/rls#schema-workflow)); the manifest records which, and better-supabase's doctor names the matching grants command.

Then hand the provider to better-supabase. The config runs in Node, so it reads the two files directly:

```ts title="better-supabase.config.ts"
import { readFileSync } from "node:fs";
import { defineConfig } from "better-supabase/config";
import { authorizationProvider } from "permdock/better-supabase";

const read = (file: string) =>
  readFileSync(new URL(file, import.meta.url), "utf8");

export default defineConfig({
  auth: {
    authorization: authorizationProvider({
      manifest: read("permdock.manifest.json"),
      catalog: read("permissions.catalog.json"),
    }),
  },
  blocks: { permissions: { model: "provider" }, organizations: {} },
});
```

Run `better-supabase upgrade` and `better-supabase gen` after a change to the policy, so the rendered SQL and the provider agree. Rerun `permdock supabase inspect --out` first.

### Claims

Validate sessions with the claim contract's Standard Schema, extended with the app's own claims:

```ts title="src/lib/supabase/index.ts"
import { defineSupabase } from "better-supabase";
import { supabaseClaims } from "permdock/supabase";
import { z } from "zod";
import { schema } from "./generated";

export const betterSupabase = defineSupabase(schema).claims(
  supabaseClaims().extend(
    z.object({ datetime_preferences: z.object({ timezone: z.string() }) }),
  ),
);
```

A token whose claims fail either schema resolves to an `invalid` session. Pass `supabaseClaims({ tenantClaim })` when `rls.tenantClaim` is not `tenant_id`, and set the same name in better-supabase's `auth.organization.claim`.

### Memberships

PermDock's token hook writes the membership claims; the memberships block supplies the table that blocks such as share links and organizations read. Run both over one table the app declares:

1. Create the memberships table in the app's own schema file, one row per member: `(organization_id, user_id, role)`.
2. Map the block onto it with `blocks.memberships.tables.memberships`. The block runs over a table it does not own: it adds only the columns it lacks and its `bsb_` policies and triggers.
3. With the organizations block installed, set `blocks.organizations.options.assignmentGuard: "external"`. PermDock's assignment triggers then check role changes, and better-supabase drops its own guard; it refuses `"external"` on a table the block created.
4. Point PermDock's sources at the same table with `blockMembershipSource`.

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: {
    memberships: { tables: { memberships: "public.organization_memberships" } },
    organizations: { options: { assignmentGuard: "external" } },
  },
});
```

`blockMembershipSource` from `permdock/better-supabase` reads the block's logical columns: `organization_id`, `user_id`, `role` and `disabled_at`, under the `organization` scope. Rename a column through `columns`, and pass `disabledAt: null` when the table has none. A role kept in another table goes through `roleThrough` (the block's option of the same name). Several roles per member go through `roles`: a junction keyed by the membership's id, or `"many"` for the `membership_roles` table that `blocks.memberships.options.roles.many` keeps, joined on the tenant and user columns:

```ts title="permdock.config.ts"
import { blockMembershipSource } from "permdock/better-supabase";

export default {
  supabase: {
    hook: {
      memberships: [
        blockMembershipSource({
          table: "public.organization_memberships",
          columns: { disabledAt: null },
        }),
        // Several roles per member, from blocks.memberships.options.roles.many:
        // blockMembershipSource({ roles: "many" }),
        // or from your own junction:
        // blockMembershipSource({ roles: { table: "public.membership_roles", membership: "membership_id", role: "role" } }),
      ],
      claims: { features: "public.feature_claims" },
    },
  },
};
```

With `roles: "many"`, the manifest records the role set's `through.on`, and `authorizationProvider` names it as the membership's `rolesTable`, so better-supabase's role checks read every role and doctor BS411 stays quiet.

Don't let the block write the claims. `better-supabase add memberships` stops while the provider's `tokenHook.ownedClaims` lists `memberships`, and better-supabase's doctor reports BS407 for a hook that calls `membership_claims()` next to PermDock's. The `features` claim above goes through `supabase.hook.claims`.

With the provider set, the entitlements module reads membership through `member_<scope>_ids` and its `_for` form, so an expired membership or a suspended organization loses its features in the same token that loses the membership ([claims other packages own](/docs/adapters/supabase-hook#claims-other-packages-own)).

### SSO role order

The SSO block's `roleOrder` lists the roles an identity-provider group may map to, highest first, without the owner role. `roleOrderFromCatalog` derives it from the catalog's `assigns`: a role that assigns another comes before it, and roles `assigns` does not order keep catalog order. Roles that assign each other stay together at the first one's place. `scope` keeps the roles declared on that scope, and `owner` leaves that role out.

```ts title="better-supabase.config.ts"
import { parseCatalog } from "permdock/catalog";
import { roleOrderFromCatalog } from "permdock/better-supabase";

const catalog = parseCatalog(read("permissions.catalog.json"));

export default defineConfig({
  // authorization as above
  blocks: {
    sso: {
      options: {
        roleOrder: roleOrderFromCatalog(catalog, {
          scope: "organization",
          owner: "owner",
        }),
        defaultRole: "member",
      },
    },
  },
});
```

## Server code

```ts title="src/lib/access.ts"
import { getPermDockSync } from "permdock";
import { subjectFromBetterSupabase } from "permdock/better-supabase";
import { policy } from "../policy";
import { bsb } from "./supabase/server";

export async function permdockFor() {
  const session = await bsb.session();
  return getPermDockSync(policy, subjectFromBetterSupabase(session));
}
```

The same subject works in the [Hono](/docs/adapters/hono), [oRPC](/docs/adapters/orpc) and `@supabase/middleware` adapters: map `c.get("auth")`, `context.auth` or the session the middleware put on the context.

Server code that reads memberships from the database, such as a page that lists another member's rights, builds the principal from the rows with `principalFromMemberships`:

```ts
import { principalFromMemberships } from "permdock/better-supabase";

const { data: rows } = await admin
  .from("memberships")
  .select("user_id, organization_id, role, disabled_at")
  .eq("user_id", userId);
const permdock = getPermDockSync(
  policy,
  principalFromMemberships(userId, rows ?? [], {
    scope: "organization",
    tenant: organizationId,
  }),
);
```

Each organization becomes one membership `{ scope, id: organization_id, roles }`. `scope` defaults to `tenant`, the policy's first declared scope. Rows of another user, disabled rows and rows without an organization or role are dropped. A scoped grant applies only in the active organization: pass `tenant`, or pick one with `permdock.tenant(id)`, or every scoped check denies with `no-tenant`. A role the policy does not declare grants nothing ([`isRoleName`](/docs/concepts/policies#type-safety) checks one).

## Authorizer

better-supabase asks an `Authorizer` to decide each `permission` that a resource, action, route guard or MCP tool declares. `authorizer({ policy })` answers with PermDock, in process, from the claims better-supabase has already verified:

```ts title="src/lib/supabase/server.ts"
import { createNext } from "better-supabase/next";
import { authorizer } from "permdock/better-supabase";
import { permissions, policy } from "../policy";
import { betterSupabase } from "./index";

export const bsb = createNext(betterSupabase, {
  authorizer: authorizer({ policy }),
  // env, postgres and auth as before
});

export const GET = bsb.route(
  async (_request, { db }) => Response.json(await db.staff.list().orThrow()),
  { requireOrganization: true, permission: permissions.staff.list },
);
```

The adapter maps the request this way:

- The subject is `subjectFromBetterSupabase` over `subject.properties.claims`, the verified access-token claims. A `user` or a delegated `agent` subject maps through them. `anon`, `service`, a missing `claims` and anything else is the anonymous subject, so every check denies.
- `context.tenant` selects the active tenant only among the memberships the claims hold. A tenant with no membership is no tenant.
- `resource.properties` is the row, and `decide` treats it as untrusted data: a `claims` or `memberships` key in it changes nothing.
- A throw, a value that is not a PermDock permission and an unknown role deny.

| PermDock outcome    | better-supabase outcome                                                    |
| ------------------- | -------------------------------------------------------------------------- |
| `granted`           | `granted`                                                                  |
| `denied`            | `denied` with the permission key and the first denial reason as the reason |
| `approval-required` | `approval-required` with the approval token as `approval.id`               |

`evaluations` builds one PermDock instance per caller and tenant, so a list that checks each row costs one instance. `permissions: true` on a resource needs `operations`, a map from a table to the permission of each of `list`, `get`, `create`, `update` and `delete`; without it such a resource is refused. Pass `subject` to change the claim names and `options` for the sources and sinks of each instance (`customRoles`, `sink`, `limits`). `tenant`, `actor`, `delegation`, `session` and `intent` always come from the verified request.

### Options

/>

`memberships` supplies live rows when token memberships are stale or truncated. `version` reads the current authorization version; it defaults to the source's own `version` method. A generated SQL membership source does not necessarily read the version stored by the token hook: pass `authzVersion({ query })` from `permdock/supabase` when the hook's `authz_ver` is the freshness contract. `version` is the reader function, `authz_ver` is the token claim, and `principal.authzVersion` is the verified claim mapped onto the subject.

`versions` is the cache of those version reads, not a membership source. better-supabase's runtime cache takes precedence over this fallback option. It caches reads only within `maxStaleMs`; a write check reads the version live. Without `memberships`, the authorizer does not install `claimsFirst`, and `version` and `versions` do not add freshness checks on their own.

Each check builds its instance with an [`intent`](/docs/adapters/supabase#freshness-and-the-version-cache). better-supabase's request does not say whether it reads or writes, so the adapter decides:

| Check                                                               | Intent  |
| ------------------------------------------------------------------- | ------- |
| `evaluations`: list filtering and per-row checks                    | `read`  |
| `evaluate` of a permission whose action is `read`, `list` or `view` | `read`  |
| Every other `evaluate`: actions, mutations, route guards            | `write` |

Pass `intent: (request) => "read" | "write"` to decide it yourself. With `read`, `claimsFirst` may answer the version from the cache; with `write` it reads the version live.

`onError: (error, { permission, tenant }) => void` receives every error a check threw. The check still denies, and a sink that throws is ignored.

`testAuthorizer` from `better-supabase/testing` checks the adapter against the contract; `tests/better-supabase/authorizer.test.ts` runs it on a fixture policy.

## Version cache and session snapshots

One [`memoryVersionCache`](/docs/adapters/supabase#freshness-and-the-version-cache) serves both libraries. Create it and the sources once at module scope, pass the cache to better-supabase as `versions`, and pass the membership source and version reader to `authorizer`:

```ts title="src/lib/supabase/server.ts"
import { createNext } from "better-supabase/next";
import { memoryVersionCache } from "permdock";
import { authorizer } from "permdock/better-supabase";
import { authzVersion, supabasePostgresQuery } from "permdock/supabase";
import { sources } from "@/sources";

const query = supabasePostgresQuery(postgres.admin);
const memberships = sources({ query });
const version = authzVersion({ query });
export const versions = memoryVersionCache({ maxStaleMs: 5_000 });

export const bsb = createNext(betterSupabase, {
  versions,
  authorizer: authorizer({ policy, memberships, version }),
  // env, postgres and auth as before
});
```

Here `sources` is the app's generated membership-source factory. `authorizer` wraps `memberships` in `claimsFirst(source, { onStale: "reread", version, versions })` with the cache better-supabase passes at runtime. For a server created without `versions`, set `versions` on `authorizer` too. A read check answers from the cache within `maxStaleMs`; a write check reads the version live ([Authorizer](#authorizer)). `postgrestSources(...).memberships` already has a version reader; pass a separate `version` only to override it.

- `bsb.invalidateSession(userId, { tags })` forgets the user's verified session and calls `versions.evict(userId)`, so the next PermDock instance reads the version live.
- better-supabase passes `authorizer` a request-scope `memo`, and the checks of one scope share one PermDock instance per claims, tenant and intent.
- `bsb.getRequestSession()` verifies the token once per request and returns a `SessionSnapshot`. `subjectFromBetterSupabase(snapshot)` maps it like the user session of its claims, with `iat` as `Subject.issuedAt` and `authz_ver` as `principal.authzVersion`. A snapshot whose `claims.sub` is not its `userId` maps to the anonymous subject.

```tsx title="src/app/[orgSlug]/quotes/island.tsx"
async function QuotesIsland({ orgId }: { orgId: string }) {
  "use cache: private";
  const snapshot = await bsb.getRequestSession();
  const permdock = await getPermDock(
    policy,
    subjectFromBetterSupabase(snapshot),
    { tenant: orgId, memberships, intent: "read" },
  );
  // …
}
```

Other processes learn of a role or membership change through `subscribeAuthzVersions`. A trigger on PermDock's version table sends the user id on a private topic:

`admin` is a secret-key client; add no `realtime.messages` policy for `authz-versions`, so no user can join the topic. Subscribe in the module that creates `versions`. `tests/better-supabase/version-cache.test.ts` checks that `forgetSession` and `subscribeAuthzVersions` evict a shared cache.

## Storage and Realtime

```ts
import { defineBucket } from "better-supabase/storage";
import { bucketPolicy } from "permdock/better-supabase";

export const documents = defineBucket({
  id: "documents",
  path: "{organizationId}/{name}",
  policy: bucketPolicy(
    { read: permissions.documents.browse, write: permissions.documents.upload },
    { policy, scope: "organization" }, // or { manifest, catalog, scope }
  ),

```

Pass `policy` when the bucket file can import the app's policy: no JSON file is read at runtime, and `bucketPolicy` fails at definition time on a key with a conditioned grant. Pass `manifest` and `catalog` when the file cannot import the policy, for example because the policy module does not load where better-supabase reads its config.

Grant browse-style permissions per scope with no row condition for objects. `permdock doctor` PD037 reports a `storage.objects` or `realtime.messages` policy that calls a helper for such a key.

## API keys

PermDock parses better-supabase keys only when the block uses PermDock's prefix: pass `prefix: "pdk"` to `createApiKeys`. The format is the same, checksum included. The credential's id is the key's public id, the part between the prefix and the secret.

Use `apiKeyClaimOptions` where better-supabase turns a key into a token, so the token carries the claims the helpers read:

```ts
import { apiKeyResolver, createApiKeys } from "better-supabase/blocks/api-keys";
import { apiKeyClaimOptions } from "permdock/better-supabase";

const keys = createApiKeys({ transport, prefix: "pdk" });
const resolver = apiKeyResolver({
  keys,
  ...apiKeyClaimOptions(manifest),
  serviceRoles: () => ["integration"],
});
```

Use `apiKeyVerifier` where PermDock reads the key itself, for example a route outside better-supabase's middleware:

```ts
import { apiKeyVerifier } from "permdock/better-supabase";
import { subjectFromApiKey } from "permdock/server";

const subject = await subjectFromApiKey(request.headers.get("x-api-key"), {
  verifier: apiKeyVerifier({
    keys,
    manifest,
    allPermissions: Object.values(permissions),
  }),
  permissions,
});
```

`permdock/server` exports an `apiKeyVerifier` too, over PermDock's own key store. This one reads better-supabase's `api_keys` table instead; import the one that matches where the keys live.

When better-supabase's middleware already verified the key, the session is `kind: "apiKey"`. Pass `apiKeys` to `subjectFromBetterSupabase` to map it the same way:

```ts
const subject = subjectFromBetterSupabase(session, {

```

## MCP tools

Give `createMcp` the [`authorizer`](#authorizer) and set `permission` on each tool: `tools/list` hides the tools the authorizer denies, and a call is checked after its arguments validate. `toolPolicy` is the route for a permission checked on the row `data` returns.

`permdock/mcp` wraps the official MCP SDK's server, so it cannot wrap better-supabase's `createMcp`. With `createMcp`, put the permission in each tool's `meta` and spread `toolPolicy` into the options. A tool without a permission is hidden and refused. A denial's reason names the permission key and the first denial reason, as the authorizer's does. A check that throws refuses and reaches `onError`:

```ts title="supabase/functions/mcp/index.ts"
import { createMcp } from "better-supabase/mcp";
import { getPermDock } from "permdock";
import {
  subjectFromBetterSupabase,
  subjectFromShareLink,
  toolPolicy,
} from "permdock/better-supabase";
import { betterSupabase } from "../_shared/supabase.ts";
import { permissions, policy } from "../_shared/policy.ts";

type Auth = Parameters<typeof subjectFromBetterSupabase>[0];
type Instance = Awaited<ReturnType<typeof getPermDock>>;

// One PermDock instance per request: `visible` runs once per tool.
const instances = new WeakMap<object, Promise<Instance>>();
function permdockFor(ctx: { auth: Auth }): Promise<Instance> {
  let permdock = instances.get(ctx.auth);
  if (!permdock) {
    permdock = getPermDock(policy, subjectFromBetterSupabase(ctx.auth));
    instances.set(ctx.auth, permdock);
  }
  return permdock;
}

const server = createMcp(betterSupabase, {
  name: "crm",
  version: "1.0.0",
  advertisedScopes: ["openid"],
  ...toolPolicy({
    permdock: permdockFor,
    onError: (error, { permission }) => console.error(permission, error),
  }),
}).tool({
  name: "export_customers",
  description: "Export the organisation's customers as CSV.",
  meta: permissions.customers.export,
  run: (_args, { db }) => db.customers.list(),
});
```

`visible` uses `mayUse`, so a tool is listed when some grant could apply, including one with a row condition. `authorize` decides with `decide` on the row `data(ctx, tool, args)` returns, or on no row, which a row-scoped permission denies; check those inside `run` or rely on RLS. A permission that needs approval is refused, because `createMcp` has no approval store: serve those tools through [`permdock/mcp`](/docs/adapters/mcp) on the official SDK, with better-supabase's `createMcpAuth` from `better-supabase/mcp/sdk` for the bearer token and metadata. `tests/better-supabase/mcp.test-d.ts` type-checks this recipe against `better-supabase/mcp`.

## Workflows

`better-supabase/workflow-sdk` checks a permission key before a workflow hook resumes and before a web handler runs. `hookCan` and `handlerCan` answer both with `decide`, on no row unless `data` loads one:

```ts
import { authorizeHook, protectWebHandler } from "better-supabase/workflow-sdk";
import { handlerCan, hookCan } from "permdock/better-supabase";

await authorizeHook(hook, { can: hookCan(await permdockFor()) });

export const POST = protectWebHandler(handler, {
  permission: "invoices.approve",
  can: handlerCan({ getPermDock: (request) => permdockForRequest(request) }),
});
```

- `hookCan(permdock)` grants only when the caller is a member of the hook's tenant and the permission its `hookMetadata` names is `granted` there.
- `handlerCan` returns `undefined`, which better-supabase answers with 401, when the request has no signed-in principal or `getPermDock` throws. Otherwise it decides in the request's active tenant, and a denial is 403.
- An unknown key, `approval-required` and a throw are `false`.
- Without `data`, a permission with a row condition denies. `hookCan(permdock, { data: (tenant, key) => row })` and `handlerCan(source, { data: (request, key) => row })` load the row first, so the condition decides on it; a throwing `data` is `false`.

```ts
await authorizeHook(hook, {
  can: hookCan(permdock, {
    data: (tenant, key) => runs.get(tenant, hook.metadata.runId),
  }),
});
```

A better-supabase workflow run belongs to a record: its `subject` is a `RecordRef`, stored as the `bsb.subject` attribute (`type/id`), and the workflow editor starts a run on one with `start(subject_type, subject_id)`. Pass the same record to PermDock's `start(id, { resource: subject })` so the run's permissions on that type hold on that row only ([bind a run to a record](/docs/concepts/automations#bind-a-run-to-a-record)).

`tests/better-supabase/workflow.test-d.ts` type-checks both against `better-supabase/workflow-sdk`.

## Support sessions

`supportPolicy` is the `authorize` option of better-supabase's `supportSessions`. It decides each start with [`decideSupportSession`](/docs/concepts/support-sessions) as the admin, in the requested tenant:

```ts
import { supportPolicy } from "permdock/better-supabase";

const support = supportSessions({
  authorize: supportPolicy({
    policy,
    options: { settings }, // the tenant's supportSessions rules
    approved: async (_input, pending) => approvals.find(pending.token),
  }),
});
```

- The admin's verified claims become the subject, and a principal whose id is not `admin.user.id` is refused.
- A read-only start gets every `readOnlyHint` permission the admin can use. `readOnly: false` is refused unless `writable` lists the session's permissions.
- `metadata.reference` becomes the request's `reference`, for settings that require a ticket.
- An `approval-required` start passes once `approved(input, pending)` returns `{ approvedBy }` for `pending.token`, and `decideSupportSession` refuses an approver who is the admin. The token is bound to the admin, target, tenant, reason and mode, so a retried start gets the same token. `approval: false` skips approval.
- `denied`, a missing approval and a throw are `false`.

`supportPolicy` holds no approval of its own, so the app records approvals and looks them up in `approved`.

## Approvers

`approvers` names who may approve each kind of request better-supabase holds for approval. The kinds are `'ai-tool'` for a tool call, `'support-session'` for a support session, and `'<subject type>.<action>'` for the approvals block:

```ts title="better-supabase.config.ts"
import { anyOf, holder, user } from "permdock";
import { authorizationProvider } from "permdock/better-supabase";

authorizationProvider({
  manifest,
  catalog,
  approvers: {
    "ai-tool": holder(permissions.tools.approve),
    "support-session": anyOf(
      holder(permissions.support.approve),
      user(securityLead),
    ),
    "invoice.send": holder(permissions.invoice.approve),
  },
});
```

- `isApprover` is one `case` over the kind. Each branch calls `permdock_is_approver` with that kind's approvers and the request's tenant. A kind `approvers` does not name answers `false`.
- better-supabase refuses the requester before it asks, so nobody approves their own request.
- For tool calls and support sessions, `isApprover` replaces the module's default approver. Leave `'support-session'` out and only the service role can approve a support session.
- `permdock_is_approver` checks `user()` by id and `holder()` through `permitted_<root scope>_ids_by_permission` in the tenant. A role, relation or other grantee approver matches nobody in SQL and is a problem. So is a `holder()` key the catalog lacks, and a tenant scope that is not the root scope.
- With [`rls.approvals.delegations`](#approval-delegation), the manifest lists the four-argument `permdock_is_approver`, and each branch also passes better-supabase's `{requester}` and the kind's resource, so a delegate inside an active cover matches.

## Approval delegation

When both libraries are installed, PermDock owns approval delegation. Configure out-of-office covers once, in PermDock, and leave better-supabase's own delegation unused:

```ts title="permdock.config.ts"
export default {
  permissions: "./permissions.ts",
  policy: "./policy.ts",
  rls: {
    dialect: "supabase",
    authorize: "database",
    approvals: { delegations: true },
  },
};
```

- `rls.approvals.delegations` writes `approval_delegations` in the helper schema. Each row is a cover: a delegator, a delegate, an optional `tenant`, optional `resources`, and a required `from` and `until` window. A signed-in user reads the covers they gave or received, and writes only their own, in a tenant they belong to.
- It also writes a four-argument `permdock_is_approver(p_approvers, p_tenant, p_requester, p_resource)`. The check passes when the caller matches the approvers. It also passes for a delegate inside an active cover whose delegator matches them. The delegator must not be the requester, and the delegate must be a member of the tenant. The two-argument form keeps no covers.
- Rerun `permdock supabase inspect --out`. `authorizationProvider` sees the four-argument helper in the manifest and passes `{requester}`, which better-supabase fills for the approvals block, AI tool calls and support sessions.
- `tableApprovalDelegationSource({ query })` from `permdock/supabase` reads the same rows as `approvalDelegations` for [`approvalsHandler`](/docs/adapters/approvals#delegation), so an approval decided in process and one decided in SQL follow the same covers.
- A cover is checked against the delegator's own rights, one hop: the delegator's covers are never followed. A `holder()` approver through a cover needs `rls.authorize: "database"`, where `permdock_has_permission_for` and `permitted_<scope>_ids_by_permission_for` exist. In `jwt` mode only `user()` approvers pass through a cover. A cover with `permissions` set matches only in `approvalsHandler`, because the SQL check has the request kind but not its permission.

better-supabase's approvals block keeps its own `delegate_approval` for apps without an authorization provider. With PermDock installed, don't configure covers there too: the provider's `isApprover` decides who may approve, so a cover written only in better-supabase is not consulted.

## Share links

better-supabase's share-links block stores guest links: a hashed token, the subject it points at, a role, an optional expiry and a revocation. `subjectFromShareLink` turns a live row into a PermDock link principal, so a guest page decides with `can()` and reads rows under RLS through [`exchangeCapability`](/docs/concepts/capabilities#rls), the same way as a signed PermDock link:

```ts title="app/q/[token]/page.tsx"
import { subjectFromShareLink } from "permdock/better-supabase";
import { getPermDock } from "permdock";
import { exchangeCapability } from "permdock/supabase";

const subject = await subjectFromShareLink(token, {
  shareLinks, // the share-links block's client, called as anon
  links: {
    quote: {
      resource: permissions.quote,
      roles: { view: ["viewer"], comment: ["viewer", "commenter"] },
    },
  },
  ttl: 300,
});
const permdock = await getPermDock(policy, subject);
if (!permdock.can(permissions.quote.read, { id: quoteId }).granted) notFound();
const db = await exchangeCapability(subject, { key, alg: "HS256", ttl: 300 });
```

- `links` maps each share-link subject type to its PermDock resource and maps the row's role to PermDock roles. A type or role it does not name denies. The row's subject is `subject: { type, id }`; a row without it denies.
- The capability holds the row's subject id and expires at the earlier of `ttl` (default 300 seconds, at most 3600) and the row's `expiresAt`. Revoking the row stops new subjects at once; a token already exchanged lasts until its `ttl`.
- Every failure is the anonymous subject, so every check denies: an empty, unknown, revoked or expired token, a failed or throwing `resolve`, a malformed row, and a `linkPolicy` that refuses. So is a link pinned to a version (`versionId`): the capability grants the subject's current rows, so read a pinned link through better-supabase's `versions.getShared(token)`. `onAuth` receives each denial with `source: "share-link"`.
- `linkPolicy` applies [link rules](/docs/concepts/capabilities#link-policy-per-scope) to the capability. The row carries no issue time, so a `maxLifetime` rule always refuses.
- better-supabase resolves the token in its own `security definer` function, which reads only the share-link table. The guest's reads of the quote itself still go through the exchanged token and RLS.

### Feeds and calendar links

A calendar subscription or a feed reader polls one URL for months and sends no headers, so the token sits in the path. Create the link without `expiresAt` and `maxUses`: it lives until revoked, and `resolve` counts every poll as a use. Each request resolves the token again, so the first poll after `revoke(id)` gets the anonymous subject and an empty feed.

```ts title="app/feeds/[token]/route.ts"
export async function GET(
  _request: Request,
  { params }: { params: Promise<{ token: string }> },
) {
  const { token } = await params;
  const subject = await subjectFromShareLink(token, {
    shareLinks,
    links: {
      calendar: { resource: permissions.calendar, roles: { view: ["viewer"] } },
    },
    ttl: 60,
  });
  const jwt = await exchangeCapability(subject, { key, alg: "HS256", ttl: 60 });
  if (jwt === undefined) return new Response(null, { status: 404 });
  const events = await eventsUnderRls(jwt); // a client with `jwt` as its token
  return new Response(toICalendar(events), {
    headers: {
      "content-type": "text/calendar; charset=utf-8",
      "cache-control": "private, no-store",
    },
  });
}
```

- A link with no expiry still yields a capability that ends after `ttl`; keep it near the poll's own duration.
- The URL is the credential. Proxies and calendar providers log it, so offer a "reset link" that revokes the row and creates a new one.
- `no-store` keeps a shared cache from serving the feed after the link is revoked.

`tests/integration/src/better-supabase-share-link-feed.test.ts` creates a link with no expiry, reads it under RLS on two polls, revokes it and reads nothing.

## Access reviews

`accessReviewApplier` applies the revoked items of an [access review](/docs/concepts/access-reviews) through better-supabase's organizations and invitations blocks, then calls `markApplied` for each:

```ts
import { accessReviewApplier } from "permdock/better-supabase";

const apply = accessReviewApplier({
  client: supabase, // the reviewer's client
  reviews,
  policy,
  demoteTo: { admin: "member" },
  email: (userId) => directory.emailOf(userId),
});

const { applied, failed } = await apply("review_1");
```

- The review's tenant is the `organization` argument. A revoked member moves to the `demoteTo` role with `update_member_role` when no allow grant in `policy` gives that role the permission at the tenant scope. Otherwise, or without `demoteTo`, `remove_member` removes the member. A role the policy does not declare, such as a custom role, counts as granting it.
- With `email`, the tenant's open invitations to that address whose role grants the permission are revoked with `revoke_invitation`.
- Pass the reviewer's client, so the blocks' own `updateRole`, `removeMember` and role-ceiling checks run as the reviewer.
- A member who is no longer in the organization (`ORGANIZATION_NOT_MEMBER`) counts as applied. Any other error, such as `ORGANIZATION_ROLE_CEILING` or the owner invariant, leaves the item unapplied in `failed` with the message. One item's failure does not stop the others.
- With `permdockFor(principalId, tenant)`, the applier decides the permission again after the change. It does not mark applied an item the member still holds through another source, such as a global role.
- `schema` names the blocks' schema and defaults to `better_supabase`. `scope` defaults to the policy's first scope.

## Subscriber fan-out

`subscriberPolicy` filters the subscribers of an outbox event to those who may read it, with [`subscribersFor`](/docs/concepts/delivery) as the event's sender in its tenant:

```ts
import { principalSource, subscriberPolicy } from "permdock/better-supabase";

const audience = subscriberPolicy({
  policy,
  principals: principalSource({ claims: store.claims }),
  events: {
    "invoice.paid": permissions.invoices.read,
    "invoice.*": permissions.invoices.manage,
  },
});

const allowed = await audience(event, subscribers); // each subscriber has a `principal`
```

- `events` maps an event type to the permission a subscriber needs: an exact type first, then the longest `prefix.*`, then `*`. A type with no entry reaches no one.
- The row is `event.payload`, validated against the resource schema, or what `row(event)` returns.
- The sender is `event.actorId`, or what `sender(event)` returns. An event without a tenant or sender, a sender outside the tenant and a throw reach no one.

## Principals

`principalSource` loads principals for `decideFor`, `subscribersFor` and [delivery](/docs/concepts/delivery) from the claims better-supabase mints:

```ts
import { principalSource } from "permdock/better-supabase";

const principals = principalSource({
  claims: (userId, { tenant }) => store.claims(userId, { tenant }),
  identities: (identity) => links.find(identity),
});
```

- `principal(id)` maps the claims with `subjectFromBetterSupabase`. Claims for another user and `null` claims are `null`, so a deleted or suspended user reaches nothing.
- `principalByIdentity` exists only with `identities`. A `{ user }` link loads that user, and a `{ contact }` link is accepted only for a principal with `kind: "contact"`. Only links the app created through a signed-in link flow or a verified address belong there.

## Authorization hooks

better-supabase asks `AuthorizationHooks` the questions its blocks cannot answer in SQL. `authorizationHooks` answers them with PermDock:

```ts title="src/lib/supabase/server.ts"
import { createServer } from "better-supabase/server";
import { authorizationHooks, principalSource } from "permdock/better-supabase";

const principals = principalSource({
  claims: store.claims,
  identities: links.find,
});

export const server = createServer(betterSupabase, {
  authorization: authorizationHooks({
    policy,
    claims: store.claims, // (userId, { tenant }) => the claims better-supabase mints now
    service: (tenant) => store.serviceClaims(tenant),
    principals,
    events: { "invoice.paid": permissions.invoices.read },
    approvers: { "ai-tool": holder(permissions.tools.approve) },
    support: { options: { settings } },
    tickets: (ticket) => runs.ticket(ticket),
  }),
});
```

- `automation.mayPublish` lets a user publish an automation only with every key it uses granted to them in its tenant. `automation.runAs` loads the publisher's current claims, or `service(tenant)` for an organization-owned automation, checks every key again, and adds the automation's keys as `bsb_permission_cap`. A deleted or suspended publisher, a key they lost and a missing `service` run as no one.
- `delegation.permissions` maps a token's OAuth scopes to the keys whose `.scope` they are or were renamed from, and to the keys a policy `oauthScopes` entry covers. It reads no `authorization_details`.
- `approverOf` exists with `approvers`. It refuses the requester and claims whose `sub` is not the approver, then matches `user()` by id and `holder()` with `decide` in the request's tenant.
- `identities.principalByIdentity` exists when `principals` has `principalByIdentity`; a contact maps to `{ kind: "contact" }`. `delivery.subscribers` and `delivery.audience` are `subscriberPolicy` and exist with `principals` and `events`.
- `support.authorize` is `supportPolicy` and exists with `support`.
- `tickets.subject` exists with `tickets`. It looks the ticket up, then loads the user's current claims, so a suspended user's ticket is refused.
- Every hook builds the subject from the claims `claims` loads, never from the request, and fails closed: a throw, an unknown key and `approval-required` refuse.

`tests/better-supabase/hooks.test.ts` runs `testAuthorizationHooks` from `better-supabase/testing` on them.

## OAuth scopes

better-supabase narrows a delegated token (one with `client_id` or an agent `act`) inside `member_can`, `member_can_while_deleting`, `platform_can` and `tenant_ids_with`: a permission passes only when one of the token's scopes maps to it through the provider's `delegation.scopes`. A policy's coarse [`oauthScopes`](/docs/standards/oauth-agent-delegation) reach that map through the catalog:

```ts title="policy.ts"
definePolicy(permissions, {
  oauthScopes: {
    "mcp:read": [permissions.task.read],
    "mcp:write": [permissions.task.read, permissions.task.update],
  },
  // ...
});
```

```json title="permissions.catalog.json"
"oauthScopes": [
  { "scope": "mcp:read", "permissions": ["task.read"] },
  { "scope": "mcp:write", "permissions": ["task.read", "task.update"] }
]
```

`authorizationProvider` merges each entry into `delegation.scopes` next to the per-permission scopes and the former scopes of renamed keys, so a token with `scope: "openid mcp:read"` passes `member_can('task.read')` and fails `member_can('task.update')`. A key the catalog does not list is dropped. Run `permdock collect` after changing `oauthScopes`; doctor [PD070](/docs/cli/doctor#pd070-oauthscopes-missing-from-the-catalog) warns when the catalog lacks them. `tests/integration/src/better-supabase-oauth-scopes.test.ts` runs that token through better-supabase's generated SQL.

PermDock's own SQL helpers (`permitted_<scope>_ids`, `permdock_has`, the table policies) narrow by token scope with [`rls.tokenScopes`](/docs/cli/rls#token-scopes). They then read the same map through `permdock_token_scope_allows`, so a module check and a row policy agree about the same token. Without it, a delegated token that reaches the Data API keeps the user's row access there. `deny(…, { to: actor("oauth-client") })` is the blunter rule: it refuses a key to every token with `client_id` or `act`, for writes an OAuth client must never make through PostgREST. `permdock_api_key_allows` reads the backend-set `api_key.scopes` claim, which is a different ceiling.

## Agents and tool approval

better-supabase's `createAgentRuntime({ toolApproval })` from `better-supabase/ai-sdk/agents` takes an AI SDK tool-approval function and combines it with the tenant's `ask` tools; the stricter answer wins. `toolApproval` and `composeToolApproval(...)` from [`permdock/ai-sdk`](/docs/adapters/ai-sdk) are such functions: a call PermDock answers `approval-required` asks for the user's approval, and a denied call is refused. `tests/better-supabase/agents.test-d.ts` type-checks the pairing.

## Agent and team claims

Three claims shape what an agent or a team member reaches. PermDock and better-supabase each read some of them, in different places:

| Claim           | better-supabase                                                                                               | PermDock                                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `act.read_only` | `actor_may_write()` guards module tables and its own security-definer writes                                  | `permdock_actor_may_write()` guards app tables under `rls.readOnlyActors`; in process, `readOnly` denies a permission without `readOnlyHint` |
| `act.tools`     | `assertToolDelegated` in `better-supabase/ai-sdk/agents` throws `AGENT_TOOL_NOT_DELEGATED` before a tool runs | `subjectFromSupabase` maps it to `actor.tools`; the agent kernel and adapters deny any other tool with `agent-tool-not-delegated`            |
| `team_ids`      | not read; module checks call `team_ids_of(auth.uid())`, which calls `teamIdsOf`                               | the hook writes it from `supabase.hook.teams`; conditions read `principal.claims.team_ids` in process; generated RLS does not read it        |

- **Read-only agents.** `authorizationProvider` sets `functions.actorMayWrite` to `permdock_actor_may_write()` when the manifest lists it, so both libraries answer the same for module tables. App tables follow `act.read_only` only when `rls.readOnlyActors` is set: each write policy then gets a restrictive `<table>_<verb>_read_only_actors` twin. Without it, a read-only agent token still writes every app table its user may write, because the generated policies do not read `act`.
- **Tools.** Neither check exists in SQL. A delegated tool list stops an agent at the tool call, in the server; a token that reaches the Data API directly keeps its user's row access, narrowed only by `read_only`.
- **Teams.** `team_ids` is a PermDock claim, and only process-side conditions read it; RLS on team rows joins the membership table instead. `authorizationProvider` fills `teamIdsOf` with `member_team_ids_of(user)`: from the membership sources of a `team` scope, or else from `supabase.hook.teams`. With a team scope, keep `supabase.hook.teams` on the same membership table, so `team_ids_of()` and the claim list the same teams.

An agent token also needs a policy delegation to `actor("agent")`; without one, `permdock/ai-sdk` denies every tool with `no-delegation`. The example delegates its owner's `quotes` permissions:

```ts
delegations: [
  { from: roles.owner, to: actor("agent"), permissions: [permissions.quotes] },
],
```

`apps/examples/next-better-supabase/src/agent/tools.ts` binds two tools, `quotes.read` and `quotes.update`, through `permdock/ai-sdk`. `tests/stack/agent.stack.test.ts` signs tokens through the PermDock hook against the local stack (`pnpm test:stack`):

| Token `act`                                 | `quotes.read` | `quotes.update` tool       | `update public.quotes` as the token |
| ------------------------------------------- | ------------- | -------------------------- | ----------------------------------- |
| `read_only: true`, `tools: ["quotes.read"]` | rows          | `agent-tool-not-delegated` | 0 rows                              |
| `read_only: true`, both tools               | rows          | denied                     | 0 rows                              |
| `read_only: false`, both tools              | rows          | approved, the row changes  | every row the owner may update      |

## Module permission keys

better-supabase's SQL modules check permission keys, such as `audit.read`, `api_keys.manage` and the AI, workflow and inbox modules' keys. Its doctor reports a key the provider's `permissions` lacks, so pass `catalog` and declare each key the installed modules check in the policy. Rename a key with `blocks.<block>.permissions` in `better-supabase.config.ts`; doctor PD079 lists each key a configured block checks that the catalog lacks ([doctor](/docs/cli/doctor)). The example declares the audit block's `audit.read` and `audit.revert` on an `audit` resource with no table: set `rls.tables.audit: false`, or `rls generate` writes policies for a `public.audit` table the block does not create.

The attachments and comments blocks take per-subject keys from the subject registry, `subjects.<type>.permissions` in `better-supabase.config.ts`: `upload` and `manage` for attachments, `create` and `moderate` for comments. Point each at a catalog key of the subject's resource, such as `contracts.update` for `upload`, so a member who may not update a contract cannot attach files to it. The registry's `read` stays the key for the subject row; set the files' own `read` in `blocks.attachments.on.<type>.permissions`. Without per-subject keys, any tenant member with `attachments.read` reads every subject's files, and better-supabase's doctor warns with BS345 when the subject table's policies check more than tenant membership.

## Audit the PermDock tables

better-supabase's audit module registers a table with `better_supabase.audit(target regclass, …)`, which creates the audit trigger and reads the table's primary key. [`rls.audit`](/docs/cli/rls#triggers-and-audit) writes that call into the generated SQL for the custom-role tables, so every save through `permdock_replace_custom_role_grants` leaves an audit row:

```ts title="permdock.config.ts"
rls: {
  customRoles: true,
  audit: {
    function: "better_supabase.audit",
    tables: ["custom_role_permissions", "custom_role_includes"],
    args: { category: "permissions", tenant_column: "tenant_id", label_column: "role" },
  },
},
```

The arguments apply to every listed table, so `user_roles`, which has no `tenant_id`, needs a second call of your own or no `tenant_column`. Apply better-supabase's migrations before PermDock's, because the function must exist when the call runs.

## When to use bucketPolicy and topicPolicy

`bucketPolicy` and `topicPolicy` decide in better-supabase's Storage and Realtime policies through the provider's helpers, for buckets and topics defined with `defineBucket` and `defineTopic`. PermDock's own `rls.storage` and `rls.realtime` write the policies on `storage.objects` and `realtime.messages` from `permdock rls generate` instead. Pick one per bucket or topic: both on the same one write two policies that Postgres combines with `or`.

## Sessions and actors

- better-supabase's `checkSession(sql, auth)` checks that a token's session is still in `auth.sessions`. Call it before a sensitive action and pass the result as `liveSession` ([live sessions](/docs/adapters/supabase#live-sessions)).
- A support session and `actingAs` write `act` with `kind: "support"` or `"impersonation"`, so the subject's actor has that kind and every call denies with `no-delegation` until the policy names the actor in a [delegation](/docs/security/delegation#policy-delegations) ([support and impersonation actors](/docs/adapters/supabase#support-and-impersonation-actors)).
- The `scopes` guard answers 403 `insufficient_scope` before PermDock runs; PermDock's delegation narrowing still applies after it.
- Only `allow: ["anonymous"]` admits a `signInAnonymously()` user past a guard. Pair the default `allow: ["user"]` with `anonymousSignIns: "deny"` ([anonymous sign-ins](/docs/adapters/supabase#anonymous-sign-ins)).
