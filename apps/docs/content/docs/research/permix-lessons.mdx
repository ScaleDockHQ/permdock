Source: study of `letstri/permix` v4.1.2 (617 stars, MIT, single npm package with subpath adapters) and the 28 issues in the tracker. Data gathered with the GitHub CLI on 2026-09-06. permix is the closest existing library to PermDock in adapter breadth, which is why its shipped design and issue tracker are a concrete list of requirements.

## The permix core, briefly

Permissions in permix are declared purely as a TypeScript generic; nothing about the schema exists at runtime:

```ts
createPermix<{ post: ['create', 'read'] }>()
createPermix<{ post: [{ name: 'edit'; type: Post; required: true }] }>()
```

The instance is a closure over mutable `rules` and `ready`. `setup(rules)` replaces the whole tree and mutates the shared instance; `check('post.edit', post)` returns a boolean and throws `PermixNotReadyError` if no rules exist; `dehydrate()` collapses the tree to JSON booleans by invoking function rules once with no data; `hydrate(state)` restores booleans but deliberately does not set `ready`, forcing the client to call `setup()` again to restore function rules. `getRules()` returns the live rules object. Every server adapter works around the mutable core by creating a fresh instance per request and stashing it on the request under a `Symbol('permix')` key. Core is 2.64 kB gzip with zero runtime dependencies, ships agent skills in `permix/skills/`, and serves `llms.txt`.

Adapters shipped today: `react`, `vue`, `solid`, `svelte`, `next`, `tanstack-start`, `node`, `server`, `express`, `hono`, `fastify`, `elysia`, `trpc`, `orpc`, `effect`, `drizzle`. The Drizzle adapter only derives resource keys from table names; it does not generate `where` clauses.

## Issues and what they mean

| Issue | What happened | Meaning for PermDock |
|---|---|---|
| [#27](https://github.com/letstri/permix/issues/27) | Global `setup()` leaked permissions between concurrent requests; the answer was "use the Hono adapter". The reporter also hit that `setupMiddleware` returns an untyped `MiddlewareHandler`. [#4](https://github.com/letstri/permix/issues/4) reported the same in 2025. | Instances are immutable and request-scoped by construction; adapter middleware is typed. |
| [#22](https://github.com/letstri/permix/issues/22) | Denied-permission reason requested; closed by pointing at `onForbidden`. | `decide()` returns denials with `role` and `reason` ([decisions](/docs/concepts/decisions)). |
| [#25](https://github.com/letstri/permix/issues/25) | Real ReBAC (Zanzibar-style relations, graph traversal, ORM-inferred relations) closed by pointing at a docs page showing closures. | Async `context` on `definePolicy` for relation lookups, `subject.context` keys in portable conditions, and a bridge to OpenFGA / SpiceDB via a provider rather than a relation graph in core. |
| [#36](https://github.com/letstri/permix/issues/36) | Better Auth integration, opened after a plugin was merged and later removed; "many ways to do it". | `permdock/better-auth` layers on `createAccessControl` roles ([better-auth adapter](/docs/adapters/better-auth)). |
| [#38](https://github.com/letstri/permix/issues/38) | Audit callback on every check; the result was wanted but only `{ path, data }` was added. | `on('decision')` carries outcome, reasons, actor and delegation ([audit and observability](/docs/concepts/audit-and-observability)). |
| [#39](https://github.com/letstri/permix/issues/39) | Published `.mjs` contained raw JSX (`jsx: preserve`), breaking Vite consumers. | `publint` and `arethetypeswrong` in CI, `tests/bundle` importing each entry in a consumer-style build. |
| [#49](https://github.com/letstri/permix/issues/49) | TanStack Start: server-only imports inside the `setupMiddleware` callback leaked into the client bundle (Prisma, Better Auth in the browser); `createSetupHandler` was added as an escape hatch. | The definition module has no rules and no secrets so it is safe everywhere; the policy is server-only; explicit factory files keep server imports out of client entries ([ADR 0006](/docs/decisions/0006-explicit-factory-not-plugin)). |
| [#18](https://github.com/letstri/permix/issues/18) | Convex integration, open. | `permdock/convex` provider (Phase 4). |
| [#26](https://github.com/letstri/permix/issues/26) | Expose permix as an HTTP PDP so Go and Rust services can call TS-authored policy. | `permdock/authzen` serves the AuthZEN 1.0 endpoints ([ADR 0011](/docs/decisions/0011-authzen-wire-format)). |
| [#20](https://github.com/letstri/permix/issues/20), [#10](https://github.com/letstri/permix/issues/10) | Per-action data types and `required` data; drove the v4 action-spec redesign. The author of #20 published `access-mini` because "it's hard to make a nice typesafe api for this". | Arity is part of the reference type: `actions` take an instance, `collection` actions do not ([ADR 0004](/docs/decisions/0004-actions-vs-collection)). |
| [#28](https://github.com/letstri/permix/issues/28) | Multiple instances in one oRPC context (permissions plus feature flags) needed a configurable `contextKey`. | Nested groups in one definition cover most cases; adapters accept a context key. |
| [#33](https://github.com/letstri/permix/issues/33) | Elysia `checkHandler` typed against raw `Context`, breaking with validated routes. | Adapter generics preserve the framework's own context type. |
| [#46](https://github.com/letstri/permix/issues/46), [#41](https://github.com/letstri/permix/issues/41), [#40](https://github.com/letstri/permix/issues/40) | TanStack Start: instance unavailable in `beforeLoad` / `loader`, symbol context keys stripped, docs wrong; led to a two-instance design. | Snapshots are plain JSON and travel through any router context. |
| [#47](https://github.com/letstri/permix/issues/47) | `llms.txt` returned 404; users expect LLM-oriented docs. | `llms.txt`, `llms-full.txt`, `.md` per page from the first docs deploy. |
| [#16](https://github.com/letstri/permix/issues/16), [#15](https://github.com/letstri/permix/issues/15) | RPC adapters initially exposed only `check`, no `dehydrate` or `template`. | Every adapter exposes the full `PermDock` instance. |
| [#11](https://github.com/letstri/permix/issues/11) | NestJS integration, opened June 2025, still open. | `permdock/nest` (Phase 2). |

## Pain points to design against

- Hydration collapsed function rules to booleans and forced a duplicated client `setup()`; every SSR page in the permix docs carries a warning box about it, and Solid, Svelte and Vue had first-render bugs. PermDock snapshots carry portable conditions, so the client evaluates ownership checks itself ([snapshots](/docs/concepts/snapshots)).
- The audit hook lacked the result (#38).
- No real ReBAC or async relation resolution (#25).
- Server-only imports leaking into client bundles (#49).
- Untyped middleware generics (#27, #33).
- Raw JSX shipped in `.mjs` (#39).
- Schema exists only at the type level, so there is no runtime catalog, no admin UI listing, and no validation of `check()` payloads.

## Adopt / adapt / avoid

Adopt:

- One npm package with subpath exports rather than `@permix/*` scoped packages ([ADR 0002](/docs/decisions/0002-umbrella-package)).
- Zero runtime dependencies in core. Per-entry gzip size is measured; a regression budget is set from the Phase 1 baseline ([ADR 0020](/docs/decisions/0020-measure-bundle-size-then-set-a-baseline)).
- Agent skills shipped inside the npm package, `llms.txt` and `llms-full.txt` on the docs site.
- Per-request instances stashed on the framework's request context in HTTP adapters.
- Type-aware Oxlint and Oxfmt, tsdown, pnpm catalogs, Turborepo.

Adapt:

- permix's Next.js adapter memoises a per-request instance with React `cache()`. PermDock keeps that as `createPermDock` in `permdock/next` with `getPermDock()` memoised the same way.
- Type-only definitions become `resource(Schema, ...)` with boundary validation instead of per-call parse options.
- A separate catalog extractor is unnecessary: because permissions are typed references the definition is already the catalog, and `permdock collect` scans usages for coverage.
- Boolean `check()` plus a later `explain()` becomes a single `decide()`; there is no separate boolean-plus-explain pair.
- Each adapter copying request isolation becomes a Fetch-first server kernel with thin adapters. Factory-only UI hooks are dropped, because reference-typed hooks need no factory.
- Auth provider adapters stay, with the HTTP PDP replaced by AuthZEN.

Avoid:

- Type-only definitions with no runtime shape.
- A mutable singleton with `setup()`; any API where the first call flips a global `ready` flag.
- Boolean-only hydration that requires the client to re-declare rules.
- Template-literal string paths (`'post.edit'`, `'post.~all'`) as the public API.
- Audit hooks without the outcome.
