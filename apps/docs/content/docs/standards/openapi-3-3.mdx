## What it is

OpenAPI 3.3 is the next minor version of the OpenAPI Specification. Nothing about it is final. What the OpenAPI Initiative has published so far:

| Fact | Source |
| --- | --- |
| Development happens on branch `v3.3-dev`; 3.1.3 is on `v3.1-dev`, 3.2.1 on `v3.2-dev`, and 4.0.0 (Moonwalk) exists only as discussions in the `OAI/sig-moonwalk` repository | [CONTRIBUTING.md branch table](https://github.com/OAI/OpenAPI-Specification/blob/main/CONTRIBUTING.md) |
| The `v3.3.0` milestone stands at 16 of 38 issues closed (42%) | [Milestones](https://github.com/OAI/OpenAPI-Specification/milestones) |
| 3.3 is described as "strictly compatible with both 3.1 and 3.2", with "more comprehensive updates to parameters, form data modeling, and security configurations" | [Milestones](https://github.com/OAI/OpenAPI-Specification/milestones) |
| New approaches are created alongside frozen older ones, as steps toward Moonwalk (4.0) | [Milestones](https://github.com/OAI/OpenAPI-Specification/milestones) |
| 3.3 "promises to be one focused on API Security, with investigations already taking place on supporting the FAPI 2.0 Security Profile and Grant Negotiation and Authorization Protocol (GNAP)"; discussions have started on "what a Security Profile might look like" | [OAI newsletter, June 2026](https://www.openapis.org/blog/2026/06/09/openapi-initiative-newsletter-june-2026) |
| 3.3 is evaluating Standardized API Features (SAFs): features whose behaviour is defined by an external specification such as an RFC and that need an exception to the normal description rules; cookies (RFC 6265) is the example | [OAI newsletter, June 2026](https://www.openapis.org/blog/2026/06/09/openapi-initiative-newsletter-june-2026) |

Two of those threads intersect PermDock directly. A **Security Profile** construct would give a document a standard place to say "this API's OAuth deployment follows FAPI 2.0" instead of a vendor extension. **GNAP** support would add a security scheme type whose access rights are structured objects, the same shape PermDock already maps from RFC 9396 `authorization_details` ([GNAP](/docs/standards/gnap), [subject](/docs/concepts/subject)).

## Why it matters for PermDock

PermDock's OpenAPI output exists so that machines, including agents, can discover what a route requires before calling it. Today that is scopes, `oauth2MetadataUrl`, the device flow and `x-permdock-*` extensions ([OpenAPI 3.2](/docs/standards/openapi-3-2)). A native security-profile field would let a client discover that tokens must be sender-constrained and that query-parameter tokens are refused, which is what PermDock's FAPI 2.0 alignment enforces on the server side ([FAPI 2.0](/docs/standards/fapi-2)). A native GNAP scheme would let a document describe structured access rights, which is closer to a permission leaf than a scope string is.

Because 3.3 is declared strictly compatible with 3.1 and 3.2, adopting it should be additive: whatever PermDock emits for 3.2 stays valid, and new fields appear only when `--target 3.3` is selected.

## What PermDock does today

The profile declaration is an extension in PermDock's own namespace ([OpenAPI registries](/docs/standards/openapi-registry)):

```json
{
  "components": {
    "securitySchemes": {
      "permdockOAuth": {
        "type": "oauth2",
        "oauth2MetadataUrl": "https://auth.example.com/.well-known/oauth-authorization-server",
        "x-permdock-securityProfile": "fapi2",
        "flows": { "authorizationCode": { "authorizationUrl": "https://auth.example.com/authorize", "tokenUrl": "https://auth.example.com/token", "scopes": { "post:delete": "Delete a post you own" } } }
      }
    }
  }
}
```

- `x-permdock-securityProfile` is written on the security scheme by `permdock openapi emit --profile fapi2` or the adapter option `securityProfile: 'fapi2'`, and may be repeated on an operation to override the scheme's value for that operation.
- The only value today is `fapi2`. It declares the resource-server requirements of the FAPI 2.0 Security Profile: tokens accepted in the HTTP header only (bearer per RFC 6750 or DPoP per RFC 9449), never in query parameters; validity, expiry and revocation verified; sender-constraining via mTLS (RFC 8705) or DPoP verified. `--profile fapi2` refuses to annotate a scheme that contradicts those rules.
- The same extension is emitted for `--target 3.1`, `3.2` and `3.3`. It is the stable form; the native form does not exist yet.

`--target 3.3` is accepted by the CLI and the adapter and marked experimental. It currently produces the 3.2 shape (3.3 is compatible with 3.2) and exists so that projects can start a 3.3 document without a later flag change. Its output tracks `v3.3-dev` and may change between PermDock minor versions until 3.3.0 is released.

## Adoption plan

1. **While 3.3 is in development.** `--target 3.3` emits the 3.2 shape plus `x-permdock-securityProfile`. PermDock does not emit any field that exists only in `v3.3-dev`.
2. **When 3.3.0 is released with a Security Profile construct.** `--target 3.3` emits the native construct for `fapi2`, and keeps `x-permdock-securityProfile` on `--target 3.1` and `3.2` output. The importer reads both. A new ADR records the mapping, and this page's `Status` moves to `planned` (it gains implementation work) and then `shipped`.
3. **If 3.3.0 ships a GNAP security scheme.** `permdock/openapi` maps permission leaves to GNAP access-right objects (`type`, `actions`, `identifier`) the same way it maps them to RFC 9396 `authorization_details`, and the [GNAP](/docs/standards/gnap) page documents the scheme.
4. **Standardized API Features.** No action unless a SAF touches security; cookies as a SAF would matter only to the session-cookie handling of the framework adapters, which PermDock does not own ([authentication](/docs/concepts/authentication)).
5. **Default target.** Stays `3.2` for at least one PermDock minor after 3.3.0 is released, then moves to `3.3` behind a changeset and a note in [OpenAPI 3.2](/docs/standards/openapi-3-2).

## What would change for PermDock

| 3.3 outcome (if adopted) | Today | After 3.3.0 |
| --- | --- | --- |
| Native Security Profile field | `x-permdock-securityProfile: "fapi2"` on schemes and operations | Native field on `--target 3.3`; extension kept for 3.1 and 3.2 targets; importer reads both |
| GNAP security scheme type | Not emitted; GNAP tracked on its own page | Leaves mapped to GNAP access rights; `permdock openapi import` reads them back into keys |
| Updated security configuration objects | 3.2 `oauth2` scheme with `oauth2MetadataUrl`, device flow, `deprecated` | Same information in whichever object 3.3 defines, chosen by `--target` |
| Parameter and form-data changes | Not relevant to authorization output | No change; PermDock emits `security`, `securitySchemes`, `responses.403` and extensions only |
| Standardized API Features | None | None unless a security SAF appears |
| Moonwalk (4.0) | Not tracked beyond this page | Watched via the [watch list](/docs/standards/watch-list); no output planned |

## We do not implement drafts as if final

PermDock ships against released specifications. For 3.3 that means:

- No field from `v3.3-dev` is emitted until 3.3.0 is published, even behind `--target 3.3`. The flag exists; the draft-only content does not.
- Anything PermDock needs before then is expressed in the `x-permdock-*` namespace, which stays valid in every 3.x version and is what `--target 3.1` and `3.2` will keep using afterwards.
- The FAPI 2.0 rules PermDock enforces come from the Final FAPI 2.0 Security Profile, not from how OpenAPI might eventually describe it. Where the two differ, the OpenID Foundation document wins and the OpenAPI output follows.
- This page is updated when the milestone closes or the newsletter announces a release candidate; the `Status: tracking` line means exactly that.

## Open questions

- Whether `x-permdock-securityProfile` should accept an array (an API that satisfies several profiles) before 3.3 settles the native shape.
- Whether the default target should move to 3.3 automatically when a document's `openapi` field already says `3.3.x`, mirroring the version detection ADR 0014 describes for 3.1.
- How to validate `--target 3.3` output in CI before an official 3.3 JSON Schema exists.
