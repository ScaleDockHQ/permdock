---
title: "0046: permdock/supabase/middleware"
description: A withPermDock entry for the @supabase/middleware pipeline, on its own subpath so permdock/supabase stays peer-free. @supabase/server and @supabase/ssr are recipes.
---

## Status

Accepted, September 2026. Applies rule 3 of [0041](/docs/decisions/0041-fetch-native-frameworks-are-recipes); does not change it.

## Context

Supabase split its server-side story into three packages in 2026. `@supabase/ssr` keeps cookie sessions for Next.js, SvelteKit and Remix. `@supabase/server` is stateless: it verifies the bearer token against the project JWKS and hands the handler `jwtClaims`, an RLS-scoped client and the auth mode. `@supabase/middleware` is the engine under `@supabase/server`: `defineMiddleware` produces a `withFoo(config)` entry that contributes typed keys to a shared `ctx`, declares which upstream keys it needs, and composes through `pipeline`.

`subjectFromSupabase` already accepts the claims object `withClaims` produces, so `@supabase/server` needs no code: a recipe on the Supabase adapter page shows `subjectFromSupabase(ctx.jwtClaims, …)`. The pipeline is different. A handler that reads `ctx.jwtClaims` and calls `createPermDock` from `permdock/supabase` inline works, but every route repeats the subject wiring, the `protect` short-circuit and the Problem Details response, and nothing tells the type checker that PermDock needs `withClaims` upstream. That is the "runtime-specific hook" case [0041](/docs/decisions/0041-fetch-native-frameworks-are-recipes) rule 3 reserves for a real adapter: `defineMiddleware` is a hook with a typed contract that a `permdock/server` recipe cannot express.

The pressure the other way is [invariant 12](/docs/security/threat-model): `permdock` core has one runtime dependency. `permdock/supabase` today imports nothing from Supabase; `subjectFromSupabase` is a pure claims mapper. Adding a `@supabase/middleware` import there would make every consumer of the subject provider carry the peer.

Both packages are pre-1.0 (`@supabase/middleware` 0.5, `@supabase/server` 1.x with the pipeline helpers still marked alpha). PermDock has not shipped to npm either, so the two can move together.

## Decision

1. **A new subpath, `permdock/supabase/middleware`.** It exports `createPermDock(policy, options)` returning `withPermDock`, `permdockHandler` and `openapi`. `permdock/supabase` is unchanged and still has no peer dependency. The split mirrors `permdock/next` and `permdock/next/plugin`.
2. **`withPermDock` is a `defineMiddleware` entry.** It declares `jwtClaims` as its prerequisite, so `pipeline([withPermDock()], …)` without `withClaims` (or another contributor of `jwtClaims`) is a type error. It contributes `ctx.permdock`, a request-scoped frozen `PermDock`. `withPermDock({ protect, data })` additionally runs the kernel's `protect` and short-circuits with Problem Details, the same responses the HTTP adapters emit.
3. **`subject` stays required and callback-based.** `options.subject(ctx, request)` receives the pipeline context; the documented body is `subjectFromSupabase(ctx.jwtClaims, …)`. The entry never reads `ctx.jwtClaims` on the consumer's behalf, because the claims-to-principal mapping (`roles`, `tenant`, `schema`) belongs to the consumer, as on every other adapter. A `null` `jwtClaims` (no token, `publishable` or `secret` mode) reaches `subjectFromSupabase` and becomes the anonymous subject, never a throw ([invariant 13](/docs/security/threat-model)).
4. **`@supabase/middleware` is an optional peer.** It is imported for `defineMiddleware` and the `Middleware` type only. `@supabase/server` is not a peer: the entry types `jwtClaims` structurally (`SupabaseJwtClaims`) so it accepts `@supabase/server`'s `JWTClaims` without importing it, and any other pipeline entry that contributes the same shape.
5. **`@supabase/server` and `@supabase/ssr` are recipes.** `withClaims` plus `subjectFromSupabase` on the Supabase adapter page; `withOAuthProtectedResource` plus `permdock/jwt` on the MCP page; `withPostgresClient` on the RLS page as the runtime counterpart of `permdock rls verify`; `@supabase/ssr` session-to-subject on the Supabase page. None of them gets a package entry.

## Consequences

- One new `tests/bundle` entry (`./supabase/middleware`) and one new example, `apps/examples/supabase-middleware`, which runs real `withClaims` verification against an in-process JWKS so the e2e suite exercises the `@supabase/server` contract, not a stub.
- `getting-started/naming` gains `withPermDock` as the one middleware-style name in the package. It is the pipeline's convention (`withClaims`, `withPostgresClient`); PermDock does not adopt `with*` anywhere else.
- Catalog pins move with the alpha and beta packages. A breaking `defineMiddleware` change is a `permdock` minor until 1.0.
- `audit-permissions` gains a check: every `withPostgresAdminClient` or `ctx.supabaseAdmin` use sits behind an explicit `assert`, because that client bypasses RLS.

## Alternatives considered

- **Merge into `permdock/supabase`.** Rejected: it would make `@supabase/middleware` a peer of the subject provider that most consumers use from Hono, Next or Express without any pipeline.
- **A recipe only, under [0041](/docs/decisions/0041-fetch-native-frameworks-are-recipes) rule 1.** Rejected: the recipe cannot declare the `jwtClaims` prerequisite or contribute a typed `ctx.permdock`, so every route re-derives the instance and the composition contract lives in prose.
- **Read `ctx.jwtClaims` inside the entry and drop `subject`.** Rejected: it would hard-code one claims mapping and diverge from every other adapter's `subject` option.
- **Peer on `@supabase/server` for the `JWTClaims` type.** Rejected: a structural type is enough, and it keeps the entry usable with any contributor of `jwtClaims`.
- **Wait for 1.0 of the pipeline packages.** Rejected: PermDock is pre-release too; moving with the alpha is cheaper than retrofitting.
