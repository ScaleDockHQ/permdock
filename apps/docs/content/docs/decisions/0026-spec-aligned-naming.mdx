---
title: "0026: Spec-aligned naming for the subject and token failures"
description: Why PermDock adds principal.issuer, a structured principal.assurance, subject.session and cnf-shaped Binding members instead of renaming its subject vocabulary, why token failures adopt the RFC 6750 and RFC 9470 vocabulary as a reason plus a cause, which names stay PermDock's own with a documented mapping, and how the one actor.kind inconsistency is fixed.
---

## Status

Accepted, September 2026. Extends [0012](/docs/decisions/0012-two-principal-subject) (the `principal` / `actor` / `delegation` shape) and [0018](/docs/decisions/0018-authentication-is-upstream) (which added `expiresAt`, `principal.kind`, `principal.assurance` and `binding`). Supersedes nothing; it changes the *contents* of two fields (`assurance`, `binding`) before either has shipped.

## Context

PermDock's subject vocabulary was designed from the product inward: `principal`, `actor`, `delegation`, `binding`, `assurance`, `expiresAt`. The specifications the subject is built from were designed from the wire outward: RFC 7519 (`sub`, `iss`, `aud`, `exp`), RFC 8693 (`act`), RFC 7800 (`cnf` with `jkt`, `x5t#S256`, `jwk`, `kid`), OpenID Connect Core (`acr`, `amr`, `auth_time`, `sid`), RFC 9068 (`at+jwt`, `client_id`, `roles`, `groups`, `entitlements`), RFC 6750 and RFC 9470 (`invalid_token`, `insufficient_scope`, `insufficient_user_authentication`). The [OpenID Connect](/docs/standards/openid-connect) and [JOSE](/docs/standards/jose) pages, and the [JWT adapter](/docs/adapters/jwt) they specify, meant every claim had to be placed in the subject, and every token failure had to be rendered as an HTTP challenge. That forced an audit of every place where PermDock's name and the spec's name differ.

The audit over the docs tree (term counts at the time: `actor` on 305 lines in 63 files, `binding` 50 lines in 23 files, `cnf` 21 lines in 6 files, `expiresAt` 47 lines in 25 files, `authorizationDetails` 41 lines in 13 files, `assurance` 23 lines in 12 files) found four kinds of difference:

1. **Names the specs have that PermDock lacked.** No `iss` anywhere on the subject, so two issuers minting the same `sub` would collide in grants and audit. `acr`, `amr` and `auth_time` were collapsed into one `assurance: string`. `sid` had no home, so a `logout_token` or a CAEP `session-revoked` event could only be matched by principal id, not by session. `.well-known/openid-configuration`, `jwks_uri` and `invalid_token` did not appear in the docs at all.
2. **Names PermDock has that the specs spell differently, on purpose.** `actor` for RFC 8693 `act`, `delegation.scopes` for `scope`, `authorizationDetails` for `authorization_details`, `expiresAt` for `exp`, `jwks` / `issuer` / `audience` for `jwks_uri` / `iss` / `aud`. These are camelCase TypeScript names for JSON claims and read correctly in a policy file; renaming them to the wire spelling would make `subject.exp` and `subject.act` the public API.
3. **A field whose members did not round-trip.** `Binding` was `{ method: 'dpop' | 'mtls', thumbprint }`: a PermDock-invented shape for what RFC 7800 already defines as `cnf` with `jkt` (RFC 9449) and `x5t#S256` (RFC 8705). A verifier in another language, or PermDock's own signed outputs, would have to translate.
4. **A vocabulary PermDock invented where one already existed.** `on('auth')` reasons were a flat list of causes (`expired`, `invalid-signature`, `wrong-audience`, `token-in-query`, `alg-not-allowed`, `sender-constraint-required` and others) with no relation to the three error codes an HTTP adapter has to emit. Every adapter would need its own table from cause to RFC 6750 code. Separately, `actor.kind` for MCP clients was `'mcp'` on three pages and `'mcp-client'` on two, and the JWT adapter carried an `'oauth-actor'` placeholder.

The rule for [0005](/docs/decisions/0005-naming-convention) was "the brand is the noun". It said nothing about the case where a *specification* is the noun.

## Decision

1. **Where a specification names a concept, PermDock uses that name or maps to it exactly once.** The mapping lives in one table, "Spec names" on [naming](/docs/getting-started/naming), mirrored on [subject](/docs/concepts/subject). PermDock never coins a second spelling for a concept a specification already names; adding a field that a specification names requires a row in that table first.
2. **Add, do not rename, for the missing claims.**
   - `principal.issuer: string`, from `iss`. Every `subjectFrom*` sets it. Identity in grants, memberships, approvals and audit is `issuer` + `id`, never `id` alone; two copies of `sub: "1234"` from two issuers are two principals.
   - `principal.assurance` becomes an object `{ acr?: string; amr?: string[]; authTime?: number }`, from `acr`, `amr` and `auth_time` (OIDC Core section 2, RFC 8176 for `amr` values). Providers that expose a single level map it into `acr`: Supabase `aal` becomes `assurance.acr: 'aal2'`. A condition reads `subject.assurance.acr`, and a failed one produces the Decision reason `insufficient-user-authentication` (item 5).
   - `subject.session?: string`, from `sid`. It is the join key for Back-Channel Logout tokens and CAEP `session-revoked` events and is carried in snapshots so a client can drop the right one. It is not on `principal` because it identifies the session, not the person.
3. **`Binding` keeps its name; its members become RFC 7800 `cnf` members.** `binding` was named after FAPI 2.0's "sender-constrained" and stays, because "sender constraint" is what a policy author looks for. Its shape is now `{ jkt?: string; 'x5t#S256'?: string; jwk?: JsonWebKey; kid?: string }`, the `cnf` object verbatim, so `subject.binding` equals the token's `cnf` and round-trips into signed outputs and into another language without translation. The method is implied by the member (`jkt` is DPoP, `x5t#S256` is mTLS). A binding with none of the four members is not a binding.
4. **Keep, with a documented mapping**, the names in the second category: `Subject`, `principal`, `actor`, `delegation` (0012; `actor` is RFC 8693 `act`, innermost `act.sub` is `actor.id`, the nesting is `delegation.chain`), `delegation.scopes` (`scope`, space-separated on the wire), `delegation.authorizationDetails` (RFC 9396 `authorization_details`), `delegation.access` (RFC 9635 / RFC 9767 `access`), `expiresAt` (`exp`; NumericDate seconds everywhere, so `Subject`, `Membership`, `ApprovalRequest` and Snapshot v2 share the unit and a JWS envelope copies the value), and the `jwks` / `issuer` / `audience` / `discovery` options (`jwks_uri`, `iss`, `aud`, the Discovery document). `principal.roles`, `principal.memberships` and `principal.tenant` are PermDock concepts fed by RFC 9068 `roles` / `groups` and the provider's active organisation; they stay.
5. **Token failures adopt the RFC 6750 and RFC 9470 vocabulary as `reason`, with the specific failure as `cause`.** Every failure of `subjectFromJwt` and every `TokenVerifier` failure is `{ reason: 'invalid-token', cause }` where `cause` is one of the closed list on the [JWT adapter](/docs/adapters/jwt) (`invalid-signature`, `expired`, `not-yet-valid`, `wrong-audience`, `wrong-issuer`, `wrong-token-type`, `alg-not-allowed`, `alg-none`, `unknown-kid`, `malformed`, `encrypted-token`, `dpop-proof-invalid`, `mtls-binding-mismatch`, `sender-constraint-required`, `token-in-query`, `invalid-claims`, `jwks-unavailable`, `discovery-unavailable`, `discovery-mismatch`); that table is the source of truth and a new cause is added there first. The token becomes the anonymous subject as before; `reason` is what the HTTP adapter renders (`WWW-Authenticate: Bearer error="invalid_token"`) and `cause` is what the audit event and `permdock doctor` show. Two Decision reasons render as the other two codes: the existing `not-delegated` and `no-delegation` render as `insufficient_scope` with `scope=` from `permission.scope`, and the new `insufficient-user-authentication` renders as the RFC 9470 challenge with `acr_values` and `max_age` from the failed condition. PermDock spells these with hyphens like every other reason; the adapter writes the underscored wire form. No adapter carries a second mapping table.
6. **One `actor.kind` per runtime.** MCP clients are `'mcp-client'`, matching `subjectFromMcp` and `McpPrincipal`; the three `'mcp'` uses on the delegation, MCP authorization and OAuth agent delegation pages are corrected. An actor derived from an RFC 8693 `act` claim in a plain JWT is `'oauth-client'`; the `'oauth-actor'` placeholder is retired. The actor table on [subject](/docs/concepts/subject) is the closed list of `actor.kind` values; an adapter adds its row there before using a new one.

## Consequences

- `Subject` gains `principal.issuer` (required from every provider), `principal.assurance` as an object, `subject.session`, and `binding` with `cnf` member names. Since nothing has shipped, there is no migration; ADR 0018's `assurance: string` and `Binding` shapes are replaced in the [subject](/docs/concepts/subject) and [tenancy](/docs/concepts/tenancy) pages, and the Supabase `aal` example becomes `subject.assurance.acr`.
- The Snapshot v2 `subject` object carries `issuer`, `assurance` and `session`; this is additive within v2. Decision events carry `issuer` next to `principal.id`.
- `on('auth')` handlers switch on `cause`, not `reason`; the [FAPI 2.0](/docs/standards/fapi-2) enforcement list and the JWT adapter's behaviour table are rewritten in `reason` + `cause` form.
- HTTP adapters and `permdock/mcp` render the three RFC codes from `reason` alone. The [Problem Details](/docs/standards/problem-details) page and the denial table on [adapters](/docs/adapters) list the header for each.
- A verifier in Go, Python, Java or .NET reads `subject.binding` as a `cnf` object with no translation; the same holds for the `cnf` inside signed outputs.
- Conditions on assurance read a path (`subject.assurance.acr`) rather than a string field; the RLS compiler maps it like any other principal path.
- The rule in decision 1 is now part of the naming convention on `AGENTS.md`; a review that finds a new field whose concept a specification already names, without a row in the "Spec names" table, rejects the change.

## Alternatives considered

- **Rename everything to the wire spelling** (`subject.sub`, `subject.exp`, `subject.act`, `delegation.authorization_details`). Rejected: a policy file would read as a token dump, snake_case leaks into a camelCase API, and `act` as a field name is opaque to a policy author who has never read RFC 8693. The mapping table gives the interoperability without the cost.
- **Keep `assurance` a string and let providers pick what goes in it.** Rejected: `amr` is an array, `auth_time` is a number, and RFC 9470's `max_age` challenge needs `auth_time` specifically. One string cannot carry the three inputs a step-up condition needs.
- **Keep `Binding` as `{ method, thumbprint }` and translate at the edges.** Rejected: it made PermDock the only party with a private spelling for `cnf`, and every signed output and every non-TypeScript consumer would have to know it. Keeping the field name and adopting the member names costs nothing.
- **Make `reason` the fine-grained cause and let adapters map to RFC 6750.** This was the previous design. Rejected: each of the HTTP, MCP and A2A adapters would carry the same table, and a new cause would need updating in all of them. Putting the wire code in `reason` and the detail in `cause` means one place changes.
- **Rename `not-delegated` to `insufficient-scope`.** Rejected: `not-delegated` is a Decision reason about the intersection rule and applies equally to `authorization_details` and GNAP `access`, where RFC 6750's `insufficient_scope` is only the HTTP rendering. The Decision keeps its name; the rendering table maps it.
- **Put `session` on `principal`.** Rejected: a principal is a person or workload; a session is one login of that principal, and `memberships` and grants must not vary by session. Logout and revocation match on `session` or on `issuer` + `id`, which is why both live where they do.
