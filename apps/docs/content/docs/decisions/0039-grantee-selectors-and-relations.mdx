---
title: "0039: Grantee selectors and relations"
description: Grants target a typed grantee (role, anyone, authenticated, relation, plan, actor, assurance), not only a role; resources declare relations that compile to portable conditions.
---

## Status

Proposed, September 2026. Supersedes the "entitlements are roles" rule on [policies](/docs/concepts/policies) and the role-only grant target in [0010](/docs/decisions/0010-policy-as-data-portable-conditions). Scoped membership matching in [0024](/docs/decisions/0024-scoped-roles-and-memberships) stays; it becomes the matcher for the `role` grantee kind.

## Context

Every 0.1 grant is stamped with `role: string` and `scope`. Plans, feature flags, assurance, ownership and agent-versus-human therefore become fake roles or `subject.*` conditions. Clerk exposes four dimensions (`role`, `permission`, `feature`, `plan`). Cedar writes `permit(principal in Role::"admin", action, resource) when { resource.author == principal }`. Polar writes `"update" if "author"`. OpenFGA writes a relation.

Anonymous grants were an open question: whether `role('anonymous', ...)` applies when `subject` returns `null`.

## Decision

1. **`Grant.to` is a grantee or an intersection of grantees.** Wire kinds: `role` (with `scope`), `anyone`, `authenticated`, `relation`, `plan`, `actor`, `assurance`. `allow` / `deny` take `to`. `definePolicy` accepts a top-level `grants` array; an entry without `to` throws. `role(name, grants)` still works and stamps `to: { kind: 'role', role, scope }`.
2. **An array is an intersection.** `to: [roles.member, plans.pro]` means both must match. Separate `allow` grants still OR together. Any matching deny wins.
3. **`anyone()` includes anonymous.** It is the only selector that matches `principal: null`. `authenticated()` requires a principal. This resolves the anonymous open question: there is no magic `anonymous` role; write `to: anyone()`.
4. **Relations live on the resource node.** `relations: { author: 'authorId', org: { field: 'orgId', memberOf: 'tenant' } }`. `relation(permissions.post, 'author')` autocompletes from the node and compiles to a portable `where` (`{ authorId: principal.id }` or a `memberOf` / tenant equality). Compilers and RLS are unchanged.
5. **`Principal.plans`** is `readonly string[]`. `subjectFromJwt` maps `entitlements` (and a `claims.plans` path) there. Clerk `pla` maps there. Clerk `fea` still maps to roles.
6. **Snapshot v3** ships `grants[].to` and `vocabulary: { roles, plans }`. `parseSnapshot` accepts majors 1, 2 and 3. A v2 grant without `to` is read as `{ kind: 'role', role, scope }`.
7. **`MatchedGrant.to` and `Denial.to`** travel on the Decision and the decision event. `role` remains `string | null` for display.

Chained relations and a `features` vocabulary are deferred.

## Consequences

- Evaluation iterates `policy.grants`, not only role bindings. Role matching, tenant / team / resource scope and expiry stay inside the `role` matcher.
- `where()` and `filter()` include relation-derived conditions.
- Catalog v2 records relations on resources.
- Breaking pre-1.0: `Grant.role` / `Grant.scope` are derived from `to`; snapshot major becomes 3.

## Alternatives considered

- **Keep roles as the only grantee and document entitlements-as-roles.** Rejected: it forced every new dimension through a noun that is not true.
- **A Cedar-like `permit(principal, action, resource)` builder.** Rejected: PermDock is data, not a DSL ([0010](/docs/decisions/0010-policy-as-data-portable-conditions)).
- **A Zanzibar graph store.** Rejected: finite declared relations compile to the portable subset we already evaluate and ship to RLS. Self-referential hierarchies stay a provider's job ([roadmap](/docs/roadmap) non-goals).
