---
title: "0028: Synchronous evaluation"
description: Why can, decide, assert, filter and snapshot never await, why closure grants must return a boolean, and why explain is not an alias of decide.
---

## Status

Accepted, September 2026.

## Context

[0007](/docs/decisions/0007-decide-not-explain) left two Phase 1 questions open: whether `decide` needs an async twin for closure grants that return a Promise, and whether `explain` should exist as an alias of `decide`. Closures were typed `(data, ctx) => boolean | Promise<boolean>` while `decide` was specified as never awaiting (`concepts/decisions.mdx`). Clients, `filter` and Expo Router guards need an answer on the first frame. Async work already has a home: `context`, `MembershipSource` and `RoleSource` run once in `createPermDock`.

`explain` was proposed so agents asking "why was this denied?" would find a method. `describe(decision)` already turns a `Decision` into `{ kind, title, detail, alternatives }` for UI, Problem Details and model-readable refusals. A second name for `decide` would split the vocabulary the rest of the API standardised on.

## Decision

`can`, `decide`, `assert`, `filter`, `where` and `snapshot()` (without a `signer`) are synchronous. Closure grants are `(data, ctx) => boolean`. A thenable returned by a closure is a `closure-error` denial (fail-closed) and is reported to `on('error')`; it is never awaited. Async lookups belong in `context`, `MembershipSource` or `RoleSource`, which may make `createPermDock` itself async.

`explain` is not exported. Call `decide` for the structured result and `describe` for prose.

## Consequences

- A thenable from a closure cannot accidentally become `granted` because the caller forgot to await.
- `createPermDock` remains the only async seam on the evaluation path; adapters that already `await` the factory do not change.
- Skills and docs teach one name (`decide`) for the structured check.
- Closures that need I/O must load that I/O in `context` (or become a `MembershipSource`) so the check stays a pure function of frozen data.

## Alternatives considered

- **`decideAsync` / `canAsync` twins.** Rejected: two evaluation paths that can disagree, and an easy way to call the sync one by mistake.
- **Infer Promise from the policy.** Rejected: a single async closure would make every `can` in the UI async, including portable grants.
- **`explain` as an alias of `decide`.** Rejected: `describe` already covers discoverability; an alias would freeze a second public name.
