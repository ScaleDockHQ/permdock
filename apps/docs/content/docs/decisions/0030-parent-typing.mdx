---
title: "0030: parent is a resource name"
description: Why resource parent.resource is a string name, why a resource has exactly one parent, and when that name is resolved.
---

## Status

Accepted, September 2026.

## Context

[Tenancy](/docs/concepts/tenancy) sketched `resource({ parent: { field, resource } })` so a role held on a parent (editor on a folder) applies to descendants (documents in that folder). Open question 12 asked whether `parent.resource` is a string name or a typed reference, and whether a resource may declare two parents.

A reference (`parent: { field: 'folderId', resource: permissions.folder }`) would need the parent tree to exist in the same module, which fights `mergePermissions` across packages. A string keeps leaves plain JSON ([0008](/docs/decisions/0008-plain-json-leaves-identity-by-key)) and lets a feature package declare `parent: { field: 'projectId', resource: 'project' }` before the app merges the project definition.

Two parents would make `memberOf` hops a graph, not a chain, and would need disambiguation when both parents hold roles. Self-referential folders-in-folders were already out of scope ([tenancy](/docs/concepts/tenancy)): finite declared chains only.

## Decision

`resource(schema, { parent: { field, resource } })` takes `resource` as the resource **name string** (the last path segment, the same string as `leaf.resource`). A resource declares at most one parent. A resource must not name itself.

The name is resolved at `definePolicy` time, after any `mergePermissions`, against the definition's resource registry. An unknown parent name is a throw at policy construction, not a silent non-match at check time. `resource()` itself does not look up the parent: it only records the declaration.

## Consequences

- Feature packages can declare parent hops without importing the parent's definition module.
- Duplicate resource names in one merged tree are a throw, so parent lookup is unambiguous.
- `memberOf` `parents` is a finite list of field names along the declared chain.
- Zanzibar-style graphs stay a bridge's job.

## Alternatives considered

- **Parent as a permission-tree reference.** Rejected: it cannot cross `mergePermissions` without the parent module, and it would put a non-JSON value next to a leaf-adjacent option.
- **Several parents.** Rejected: evaluation and RLS compilation become a graph walk; one parent is enough for the declared-chain model.
- **Resolve at `resource()` time.** Rejected: the parent may not exist until merge.
