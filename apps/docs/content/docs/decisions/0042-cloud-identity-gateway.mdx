---
title: "0042: PermDock Cloud identity gateway"
description: PermDock Cloud federates upstream identity providers and offers its own OIDC endpoints; the open-source library still consumes a Subject and never verifies a token. Supersedes the authentication rejection in 0027.
---

## Status

Proposed, September 2026. Supersedes the "no authentication product" paragraph of [0027](/docs/decisions/0027-governance-first-cloud). Does not supersede 0027's governance-first sequencing, SCIM relay, meters, or invariant 15. Does not change [0018](/docs/decisions/0018-authentication-is-upstream) for the open-source library.

## Context

0027 rejected building authentication because Better Auth is free and now Vercel-owned, Clerk and Auth0 are Marketplace-native, and an identity product is operationally heavy in the way 0018 already refused for core. That evidence still holds for **replacing** Clerk or Better Auth as a general login SDK.

New evidence, specific to PermDock Cloud:

- The Cloud already publishes `/.well-known/jwks.json` and signs snapshots, approvals and decision batches. An OIDC Discovery document next to that JWKS is the missing half of an issuer, not a new product category.
- The hosted ADS already authenticates callers with Vercel OIDC or OAuth client credentials via `permdock/jwt`. Humans and agents that talk to Cloud (inbox, evidence export, MCP read-only server, device flow) need a first-party way to obtain those tokens.
- Agent Auth (Vercel / Better Auth) issues capability grants that are PermDock permission references. A Cloud device flow that mints those grants is authorization, packaged as identity.
- Applications already write `subjectFromJwt({ discovery })`. A Cloud issuer is one more Discovery URL, not a new package.

The Cloud is therefore an **identity gateway**: users can authenticate to it, and it can federate to the IdP they already have, while the embedded PDP still decides locally from a `Subject`.

## Decision

1. **PermDock Cloud is an OIDC issuer per environment.** `/.well-known/openid-configuration` sits next to the existing JWKS. Authorization code plus PKCE for humans. Device flow for agents. Tokens carry PermDock claims per [JWT authorization claims](/docs/standards/jwt-authorization-claims): roles, memberships, tenant, `authorization_details` / GNAP `access` for delegated agents.
2. **Federation.** Cloud can broker to an upstream IdP (Clerk, Auth0, WorkOS, any OIDC Discovery issuer, Google, Enterprise SSO). The upstream authenticates; Cloud issues the access token the app and the ADS consume. Cloud does not become the application's session layer.
3. **Agent Auth capability grants** on the device-flow token map to permission references (`permissions.post.delete.key` / `.scope`). No second capability vocabulary.
4. **The only open-source integration is `subjectFromJwt({ discovery: PERMDOCK_CLOUD_URL })`.** There is no `permdock/cloud-auth` entry ([0023](/docs/decisions/0023-compose-openapi-ecosystem), [0041](/docs/decisions/0041-fetch-native-frameworks-are-recipes)). `cloud({ url, key })` stays `approvals` / `sink` / `snapshots`. A later `cloud().identity` helper is deferred.
5. **Invariants hold.** Core never verifies a token (13, 0018). Cloud stays off the decision path (15, 0021, 0027). A Cloud outage leaves the embedded engine deciding from the last snapshot and the application's own `subjectFrom*`. Approvals are still not resolvable through the Cloud MCP server.
6. **Governance-first sequencing is unchanged.** The decision log still leads. Identity is a Cloud capability, not the lead meter. Meters may later add "federated connections"; they do not replace principals, tenants, approvals, retention or ADS evaluations.

## Consequences

- [0027](/docs/decisions/0027-governance-first-cloud) status line records the partial supersession.
- [authentication](/docs/concepts/authentication) gains PermDock Cloud as a Discovery source.
- [Cloud adapter](/docs/adapters/cloud) documents the issuer and the device flow. Implementation lives in the PermDock-Cloud repository.
- [threat model](/docs/security/threat-model) gains rows for the Cloud authorization-code endpoint, device flow, federated IdP compromise, and capability-grant minting.
- [commercial landscape](/docs/research/commercial-landscape) section 10 records the narrowed claim: Cloud is a gateway, not a login SDK.

## Alternatives considered

- **Leave 0027 untouched and only make the API "authn-ready".** Rejected by the product ask: Cloud should serve as an auth gateway and offer its own endpoints.
- **Ship a full authentication SDK in `permdock` (login UI, sessions, magic links).** Rejected: that is the product 0018 and 0027 correctly refused; it competes with every `subjectFrom*` provider.
- **A `permdock/cloud-auth` package.** Rejected: Discovery plus `subjectFromJwt` is the integration; a package would violate 0023.
- **Put Cloud on the decision path so hosted identity is required.** Rejected: Aserto's failure mode (0021, 0027).
