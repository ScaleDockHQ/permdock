---
title: "0051: Approval lifecycle"
description: An approval resumes exactly one call. ApprovalStore gains an atomic consume, requests record consumedAt, the token hashes only stable identity, a resume token applies only to the call it was issued for, and every approval is tenant-bound.
---

## Status

Accepted, September 2026.

## Context

Real agent loops and HTTP resumes against `memoryApprovalStore`, the Cloud client and a Postgres store showed that the approval lifecycle had gaps:

- An approved token resumed any number of calls until it expired. A human who approved one transfer approved every retry for an hour.
- `create` overwrote the record for a token, so an agent loop that asked twice reset an approval to pending.
- An approval with `approval: 'human'` and no `approvers` skipped the tenant check, so an admin of another org could approve it. The approver inbox with no active tenant listed every tenant's pending requests.
- A `PermDock-Approval` header or a resume token turned a call that needed no approval into a denial when the token was stale, and in a batch a token issued for one item denied the others. Agent adapters read the resume token from `context.approval` or `context.token`, and `token` collides with an application's own bearer token.
- The token hashed the whole principal: roles, memberships, assurance and custom claims. Refreshing a session between the ask and the resume orphaned the approval.
- The Cloud client parsed only `v: 1` approval records, so Cloud-backed approvals never resumed.

## Decision

1. **Single use.** `ApprovalStore` gains `consume(token, now?)`: an atomic transition that returns the request when it is `approved`, unexpired and unconsumed, and `null` otherwise. The request records `consumedAt`, an optional field on Approval request v2 (additive, no version bump; `status` stays `approved`). A resume that enforces the call (`protect`, agent tool execution, MCP) consumes; the decision endpoint only inspects, so a UI check never spends the approval its mutation needs. A second resume is `denied` with detail `approval-consumed`. A store without `consume` cannot resume at all (fail-closed).
2. **Idempotent create.** `create` keeps the existing record for a token and replaces it only when it has expired.
3. **Tenant-bound approvals.** A request with a tenant is resolvable only by an approver with a membership in that tenant, whether or not the grant names `approvers`. The inbox lists the requested tenant, else the active tenant, else every membership tenant; requests without a tenant appear only in the last case.
4. **Resume applies to its own call.** A resume token matters only when the decision is `approval-required` and the token equals that decision's token. Otherwise the decision is returned unchanged (and a new approval is requested when it is `approval-required`). Agent adapters read the token from the namespaced context key `permdockApproval` only.
5. **Stable token inputs.** The token hashes the permission key, the resource id, the principal's `id`, `tenant` and `issuer`, the actor's `id` and `kind`, and the condition fingerprint. It no longer hashes roles, memberships, assurance or claims; the resume still re-runs `decide`, so a role lost in between is a denial, not a grant. The `pd1.` prefix is unchanged: during a rolling upgrade, an old and a new process compute different tokens for the same call, which is a denial (fail-closed), never a grant.
6. **Public helpers.** `permdock/approvals` exports `ApprovalError` and `assertApprover` so custom stores can apply the same checks and error codes as `memoryApprovalStore`, plus `consumeApproval` and `resumeDecision`. `isApprovalError` matches by `name` and `code`, so an error from a duplicated module copy still maps to the right status.
7. **Conformance.** `testApprovalStore(store, { reopen })` covers duplicate `create`, concurrent `consume`, cross-tenant resolve and, when `reopen` is given, resume after a restart.

## Consequences

- Custom stores must implement `consume`; until they do, resumes are denied. The documented Drizzle recipe is exercised by `tests/integration` against Postgres with the conformance runner.
- PermDock Cloud must serve `POST /v1/environments/:env/approvals/:token/consume` (the approved record with `consumedAt`, or `409`) and return v2 records; the PermDock-Cloud repository follows this ADR.
- Outstanding approvals issued before the upgrade stop matching, because their tokens were computed from the full principal. They expire within their TTL.
- `memoryApprovalStore().expire()` deletes settled records one TTL after their deadline, so a long-running process no longer grows without bound.

## Alternatives considered

- **A `consumed` status.** Clearer, but a new value in a closed enum breaks every reader of Approval request v2, including the Cloud. `consumedAt` is additive.
- **Consume on the decision endpoint too.** Simpler to explain, but the React flow checks the endpoint before it posts the mutation, so the mutation would always find the approval spent.
- **Keep multi-use within the TTL.** Matches what agent runtimes do on their own, but an approval is a human saying yes to one call; replays are the threat the token exists to stop.
- **Bump the token prefix to `pd2.`.** It signals the change, but the token is opaque and a mismatch already fails closed; a prefix change would suggest a wire-format major that has not happened.
