# instant-nav rig: PermDock Next.js examples

The production rig for the `@next/playwright` `instant()` specs in `apps/examples/next` and `apps/examples/next-better-supabase`. The `next-cache-components-optimizer` and `next-partial-prefetching-optimizer` skills read this file instead of rediscovering it.

- BUILD: Playwright's `webServer` builds and serves the artifact. `next`: `next build && next start -p 3585 -H 127.0.0.1`. `next-better-supabase`: `node scripts/serve.ts` with `PORT=3589`, which starts Postgres 17 through testcontainers, applies the migrations and seed, then runs `next build` and `next start`.
- EXPOSE: `experimental.exposeTestingApiInProductionBuild: process.env["EXPOSE_TESTING_API"] === "1"` in each `next.config.ts`; the `webServer` sets `EXPOSE_TESTING_API=1` for the build. `EXPOSE_TESTING_API` is in the `build` task `env` in `turbo.json`.
- RUN: `pnpm test:instant` at the root (`turbo run test:instant --concurrency=1`: the `next-instant-navigation-testing` cookie is shared across localhost ports, so two rigs at once release each other's lock), or `pnpm --filter <example> test:instant -- <file>`. The `baseURL` comes from `tests/instant/origin.ts`. Both run a `desktop` (1280×800) and a `mobile` (390×844) project.
- TEST USER: `next`: Olivia (Acme admin) and Carol (Northwind contact), signed in by `POST /api/session` on `page.request`. `next-better-supabase`: Olivia (`…a1`, Acme owner) and Carla (`…a3`, portal contact), signed in by `GET /api/test/sign-in` on `page.request`. Seed data only; no flags; locale `en`.
- LATENCY: every `next` store read waits `DEMO_LATENCY_MS` (default 3000; `0` turns it off), which is in the `build` and `test:instant` task `env`. `instant()` renders only what is already prefetched, so a per-link or soft-navigation spec calls `settlePrefetches(page)` from `tests/instant/warm.ts` before it takes the lock. `[data-source]` footers carry `data-loaded-at`; `cold-then-warm.instant.ts` asserts that a reload and a revisit keep it, which proves the read came from the `'use cache'` layer.
- DRIFT: none known. The `next` store is in memory and the specs only read, so test order does not matter.
- CONTRACTS: `next`: initial load `/acme` (shell `[data-switch=acme]` and the `Overview` title; deferred `nav`); initial load `/portal/acme` (title; deferred `quotes`); Overview to Quotes through `[data-nav=quotes]`; organization switch through `[data-switch=globex]`; per-link `[data-quote=q-101]` (`quote` and the approve button under the lock); per-link `[data-nav=members]` (`members` under the lock); cold then warm on `/acme/quotes` and `q-101` (same `data-loaded-at`). `next-better-supabase`: initial load `/en/acme/staff` (deferred `staff`); initial load `/en/portal/acme/quotes` (deferred `quotes`); Staff to Quotes through `[data-nav=quotes]`.
- LOOP: local. Edit, run `pnpm --filter <example> test:instant`; the `webServer` rebuilds each run (about 3 s for `next`, plus the Postgres start for `next-better-supabase`). An agent can run the whole loop; Docker must be running.
- LIVENESS: n/a; local build and start.
- WALLS: A sandboxed shell points Playwright at an empty browser cache; set `PLAYWRIGHT_BROWSERS_PATH=$HOME/Library/Caches/ms-playwright`. After a soft navigation the App Router keeps the previous route as a hidden tree, so markers in soft-navigation specs need `.filter({ visible: true })`. A link with `prefetch={true}` carries `'use cache: private'` reads with a stale time of 30 s or more, so blocking such a read does not turn its soft-navigation spec RED; block with `connection()` to prove the shell spec discriminates. The server never stores a `'use cache: private'` result, so each prefetch re-runs it: keep store reads in a shared `'use cache'` function and only the check in the private one.
